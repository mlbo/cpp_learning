# C++ 项目组织、设计与思维训练教程

> 本教程是 35 天主线的工程能力辅线，不替代每天的语法、算法、EMC++ 和并发内容。它解决的是：面对一个稍大的需求时，怎样从空白开始分析、拆分、组织、验证和复盘。

很多初学者以为“能写大型项目”需要先记住一套标准目录或设计模式。真正困难的不是目录名，而是持续回答下面五个问题：

1. 系统要完成哪些行为，哪些行为明确不做？
2. 哪些数据必须始终满足什么条件？
3. 每个模块负责什么，又依赖谁？
4. 资源由谁拥有，失败和退出时由谁收尾？
5. 用什么测试证明接口承诺成立？

大型项目只是这些决定的数量更多、生命周期更长、参与者更多。训练顺序应该从一个函数、一组文件、一个构建目标逐层扩大，而不是第一天就模仿复杂开源项目。

---

## 1. 先建立正确的项目观

### 1.1 项目不是“很多代码”，而是一张受约束的协作图

可以从四个视角观察同一个项目：

| 视角 | 核心问题 | 常见产物 |
|---|---|---|
| 行为视角 | 用户要完成什么？失败时看到什么？ | 用例、输入输出、验收测试 |
| 数据视角 | 系统保存什么？哪些状态绝不能出现？ | 数据模型、对象不变量 |
| 依赖视角 | 谁调用谁？谁可以知道谁？ | 模块图、CMake target |
| 运行时视角 | 对象何时创建销毁？线程和资源怎样流动？ | 所有权图、时序图、关闭流程 |

只看文件树容易产生“目录很整齐，所以设计很好”的错觉。评价设计时要追问：需求变化时需要改几个模块？资源异常时是否仍能释放？测试能否绕开真实文件、网络或线程？

### 1.2 从小到大的五级训练

```text
函数：输入、输出、前置条件、复杂度
  ↓
类：不变量、接口、所有权、复制与移动
  ↓
构建目标：头文件、源文件、库、程序、测试
  ↓
模块：职责、依赖方向、错误边界
  ↓
系统：用例、生命周期、并发、可观测性和演进
```

某一级不稳时，不要靠增加更多抽象掩盖问题。例如一个类连不变量都说不清，先不要急着给它套工厂、观察者或依赖注入框架。

## 2. 面对新需求时的固定设计顺序

逻辑和总结能力弱时，最有效的办法不是逼自己“多想想”，而是每次都按同一顺序留下中间产物。下面这套流程适用于算法题、小项目和大型系统中的单个功能。

### 第一步：写问题卡，不允许直接写代码

```text
功能名称：
一句话目标：谁在什么情况下，要得到什么结果？

输入：
输出：
失败方式：
不做什么：

最小成功示例：
关键边界：空输入 / 单元素 / 重复 / 超大输入 / 非法状态 / 资源失败
```

“不做什么”很重要。边界不清的需求会不断扩张，最终任何模块都无法形成稳定职责。

以 Day 7 的动态数组为例：

```text
一句话目标：保存一组同类型元素，并能按下标访问和在末尾追加。
输入：元素或初始元素列表。
输出：元素引用、长度、容量，或修改后的数组。
失败方式：at 越界抛异常；内存分配失败向上传播。
不做什么：第一版不追求完全复刻 std::vector，不支持自定义分配器。
```

### 第二步：找名词、动词和规则

- 名词通常提示数据或对象：元素、长度、容量、存储区。
- 动词通常提示用例或接口：构造、访问、追加、扩容、清空。
- “必须、不能、始终”通常提示不变量和前置条件。

DynamicArray 的核心不变量可以先写成：

```text
0 <= size <= capacity
capacity == 0 时不拥有数组
capacity > 0 时存储区至少容纳 capacity 个槽位
任意时刻只有一个 DynamicArray 对象负责释放某块存储
```

先有不变量，再设计成员函数。否则每个函数各自修改状态，很容易产生一批彼此矛盾的特殊情况。

### 第三步：写最小接口，不急着写实现

```cpp
#include <cstddef>

template<typename T>
class DynamicArray {
public:
    DynamicArray();
    explicit DynamicArray(std::size_t size);

    std::size_t size() const noexcept;
    bool empty() const noexcept;

    T& operator[](std::size_t index);
    const T& operator[](std::size_t index) const;
    T& at(std::size_t index);
    const T& at(std::size_t index) const;

    void push_back(const T& value);
    void push_back(T&& value);
};
```

逐个检查接口：

- 调用者是否知道参数单位和有效范围？
- 函数会不会修改对象？能否标为 `const`？
- 会不会失败？失败后对象保持什么状态？
- 返回引用时，被引用对象能活多久？
- 是否暴露了调用者不需要知道的实现细节？

### 第四步：画所有权和生命周期

资源所有权不要只存在脑中。哪怕只画一行也比不画强：

```text
DynamicArray 对象 ──唯一拥有──> 动态存储区 ──包含──> T 元素
     析构                 逐个析构已构造元素，再 ::operator delete
```

以后遇到智能指针和并发，可以使用表格：

| 资源 | 创建者 | 所有者 | 借用者 | 释放时机 | 是否跨线程 |
|---|---|---|---|---|---|
| 动态数组 | 构造函数 | `DynamicArray` | `operator[]` 调用者短暂借用 | 对象析构或扩容成功后 | 否 |

如果“所有者”一栏写不出来，代码里往往会出现泄漏、重复释放或悬空引用。

### 第五步：先列测试，再补实现

测试不是写完以后才想起来的检查，而是接口承诺的可执行版本：

| 场景 | 操作 | 必须观察到的结果 |
|---|---|---|
| 空数组 | `push_back(1)` | `size()==1` 且首元素为 1 |
| 扩容 | 连续追加超过容量 | 原元素不丢失，容量不小于长度 |
| 复制 | 复制后修改副本 | 原对象不改变 |
| 移动 | 移动构造 | 目标得到元素，源对象仍可析构和重新赋值 |
| 越界 | `at(size())` | 抛出约定异常，对象状态不变 |

实现过程若改变接口承诺，先修改问题卡和测试，再修改代码。这样设计决定不会悄悄散落在实现细节里。

## 3. C++ 多文件项目怎样组织

### 3.1 文件是物理边界，target 才是构建边界

一个可扩展的小项目可以从下面的结构开始：

```text
project/
├── CMakeLists.txt
├── include/
│   └── project/
│       └── dynamic_array.h
├── src/
│   └── dynamic_array.cpp
├── apps/
│   └── demo.cpp
└── tests/
    └── dynamic_array_test.cpp
```

各部分职责：

- `include/`：供其他模块使用的公开接口。
- `src/`：接口实现和模块私有细节。
- `apps/`：组装库并提供程序入口，`main` 不承担全部业务逻辑。
- `tests/`：从使用者视角验证接口。
- `CMakeLists.txt`：声明构建目标及目标之间的依赖。

课程前期不强制把每一天改成这种目录。先学会解释现有结构，再在周项目中练习重组；目录服务于职责，不能反过来让简单代码变得难找。

### 3.2 头文件写契约，源文件写实现

头文件通常放：

- 类型和函数声明。
- 调用者必须知道的模板定义。
- 必要的公开常量和概念约束。

源文件通常放：

- 非模板函数定义。
- 私有辅助函数。
- 不需要暴露给调用者的第三方依赖。

不要在 `main.cpp` 中直接 `#include "something.cpp"`。这会绕过正常的翻译单元边界，容易造成重复定义，也让构建系统无法准确管理依赖。正确方式是包含头文件，并让两个 `.cpp` 同属于一个 target：

```cmake
add_library(search
    src/binary_search.cpp
)
target_include_directories(search PUBLIC include)

add_executable(search_demo apps/search_demo.cpp)
target_link_libraries(search_demo PRIVATE search)

add_executable(search_tests tests/search_test.cpp)
target_link_libraries(search_tests PRIVATE search)
```

这里 `search` 是可复用模块，`search_demo` 和 `search_tests` 是两个不同使用者。测试不需要复制实现，也不需要包含 `.cpp`。

### 3.3 为什么模板经常放在头文件或 `.tpp`

编译器实例化 `DynamicArray<Point>` 时，既要看到模板声明，也要看到成员函数定义。若定义只放在普通 `.cpp` 中，其他翻译单元通常无法为任意新类型实例化模板。

常见组织方式（下面是头文件结构片段，不是独立翻译单元）：

```cpp
// dynamic_array.h
template<typename T>
class DynamicArray {
    // 声明
};

#include "dynamic_array.tpp"
```

`.tpp` 只是帮助阅读的命名约定，本质上仍由头文件包含。也可以把全部模板定义直接放在 `.h` 中。只有明确列出并维护所需类型的显式实例化，才适合把模板定义留在 `.cpp`。

### 3.4 头文件依赖的基本纪律

1. 使用哪个标准库实体，就直接包含声明它的标准头文件，不依赖间接包含。
2. 头文件应尽量能够被单独包含并编译。
3. 能前置声明时可以减少依赖，但值成员和继承通常需要完整类型。
4. 不在头文件写 `using namespace ...`，避免污染所有包含者。
5. 公开头文件改变会触发更多重新编译，因此要谨慎暴露实现细节。

## 4. 从模块到大型项目：用依赖方向控制复杂度

大型项目最怕的不是模块多，而是依赖形成网状循环：改一个数据结构，命令行、数据库、网络和测试全部跟着改。

一个常见的起点是按职责分层：

```text
apps/main
    ↓ 组装
application/use_cases
    ↓ 调用
domain/core  ←── 定义稳定业务规则与抽象接口
    ↑ 实现接口
infrastructure/file_network_database
```

关键规则是：越接近核心规则的模块，越不应该依赖易变化的文件格式、网络库或 UI。基础设施可以依赖核心层定义的接口，核心层不反向包含某个数据库客户端。

判断模块边界时，不问“这个文件有多少行”，而问：

- 它是否只有一个主要变化原因？
- 它能否用一句话说清职责？
- 修改它时，哪些调用者必须重新理解？
- 它暴露的是业务需要，还是当前实现偶然需要？

### 4.1 用变化场景检验设计

假设正在设计一个读取数据、运行算法、输出报告的程序。先提出变化场景：

1. 输入从文本文件换成网络流。
2. 算法增加第二种实现。
3. 输出从终端换成 JSON。
4. 单元测试不能访问真实网络。

若一次变化需要修改所有层，说明职责缠在一起。更清楚的划分是：

```text
InputSource -> Parser -> DomainData -> Algorithm -> Report -> OutputSink
```

箭头表示数据或接口依赖，不表示每一步都必须创建抽象基类。只有存在真实替换需求、测试边界或独立变化原因时才增加抽象；过早抽象同样会增加理解成本。

### 4.2 大项目设计必须显式记录的内容

- 依赖方向和禁止依赖。
- 公开接口及兼容策略。
- 资源所有权和关闭顺序。
- 错误如何跨层传递，在哪里转换成用户信息。
- 线程由谁创建，共享状态由谁同步。
- 日志、指标和诊断信息从哪里获得。
- 哪些测试是单元、集成和端到端测试。

这些内容不必一开始写成长文。先用一页项目卡保持一致，遇到真正有取舍的决定再写简短设计记录。

## 5. 专门训练逻辑、归纳和总结的五张卡

### 5.1 算法推理卡

```text
问题：
朴素方法：
优化利用了什么性质：有序 / 连续 / 单调 / 可哈希 / 可重复利用状态
状态变量：
循环开始前始终成立的事实：
本轮怎样保持该事实：
为什么一定终止：
空输入和最小输入：
时间 / 空间复杂度及成立条件：
```

### 5.2 接口设计卡

```text
调用者是谁：
调用者真正需要的最小能力：
参数的有效范围：
函数是否修改对象：
返回值或引用的生命周期：
失败怎样表达：
异常后对象保证：无保证 / 基本保证 / 强保证 / 不抛异常
```

### 5.3 项目结构卡

```text
可执行程序：
可复用库：
公开头文件：
私有实现：
测试 target：
外部依赖：
依赖方向：
禁止出现的依赖：
```

### 5.4 设计决定卡

```text
背景：现在遇到什么具体问题？
候选：至少两个可行方案是什么？
决定：选择哪一个？
理由：当前最重要的约束是什么？
代价：牺牲了什么？
重看条件：发生什么变化时需要重新评估？
```

这比只写“采用某某模式”更有价值。设计模式是可选方案，约束和取舍才是决定。

### 5.5 每日知识复盘卡

不要写“今天学习了 auto、数组和双指针”这种目录式总结。使用下面五句话：

```text
1. 今天解决的核心问题是：
2. 我以前容易写错的是：
3. 正确规则成立的前提是：
4. 我用哪个测试或反例验证了它：
5. 它与上一课 / 下一课的连接是：
```

总结能力来自持续做“选择、压缩和建立连接”，不是把原文再抄一遍。

### 5.6 不会分析时使用“三遍闭环”

只填模板仍可能变成抄答案。每个重要练习至少做三遍，每一遍解决不同问题：

1. **第一遍先预测**：不看实现，填写问题卡或算法卡。允许答案不完整，但必须写出输入、边界和一个你认为成立的规则。
2. **第二遍找证据**：运行代码和测试，沿调用关系阅读实现。把每条结论对应到具体参数、分支、循环条件、数据成员或测试；没有证据的结论先标成“待验证”。
3. **第三遍做迁移**：改变一个条件，例如把“有序数组”改成“无序数组”、把“值参数”改成“引用参数”、让追加参数来自容器自身。重新判断原算法、接口或不变量是否仍成立。

最后只修订第一遍的答案，不重新抄一份标准答案。你需要留下的是“原判断 → 反例或测试 → 修正后的规则”，这样才看得见自己的推理过程。

以二分查找为例：

```text
原判断：循环条件写 left < right 或 left <= right 都可以。
证据：在闭区间 [left, right] 中，left == right 时仍有一个候选元素没有检查。
反例：数组 [5] 查找 5，若直接退出可能漏解。
修正规则：闭区间使用 left <= right；半开区间 [left, right) 使用 left < right，更新方式必须与区间定义配套。
迁移：找左边界时不在命中后立即返回，而是继续保留可能含答案的左侧区间。
```

这种记录方式同时训练逻辑和总结：逻辑体现在结论有前提和证据，总结体现在最后能把多次试错压缩成一条可复用规则。

## 7. 第一周的具体工程练习

### Day 1：画出程序怎样被构建

选择 `day_01_main`，从 `CMakeLists.txt` 找到它包含的全部源文件，再从 `main.cpp` 找到调用入口。回答：哪个文件负责组织流程，哪个文件实现算法，哪个文件提供测试数据？

### Day 2：比较三种序列接口

分别为 C 风格数组、`std::array` 和 `std::vector` 填写接口卡。重点回答：长度从哪里获得、谁拥有元素、函数能否改变长度、越界由谁负责。

### Day 3：写初始化后的对象不变量

选择一个示例类，列出每种构造方式完成后必须成立的状态。再解释为什么 `initializer_list` 构造函数参与重载会改变 `{}` 的含义。

### Day 4：把“没有对象”写进接口

找出一个返回或接收指针的函数，写清楚是否允许 `nullptr`。若允许，函数返回什么或什么也不做；若不允许，应该断言、抛异常还是改用引用。

### Day 5：区分配置和运行时状态

列出哪些值真正必须在编译期确定，哪些只是初始化后不修改，哪些需要在运行时输入。不要为了使用 `constexpr` 而强行把业务状态变成编译期常量。

### Day 6：建立第一个可复用库边界

观察二分查找的头文件、实现文件、演示程序和测试 target。解释为什么调用者包含 `.h`，而 CMake 负责把 `.cpp` 编译并链接进目标。

## 8. 怎样判断自己真的在进步

每周从 0 到 2 分评估下列项目：0 表示说不清，1 表示能在提示下完成，2 表示能独立完成并给出证据。

| 能力 | 检查问题 |
|---|---|
| 需求澄清 | 能否写出输入、输出、失败方式和不做什么？ |
| 分解 | 能否把大任务拆成职责不重叠的步骤或模块？ |
| 不变量 | 能否写出循环或对象始终保持的事实？ |
| 接口 | 能否说明参数、修改、返回生命周期和错误语义？ |
| 所有权 | 能否指出每项资源唯一或共享的责任方？ |
| 依赖 | 能否解释 target 和模块为什么沿这个方向依赖？ |
| 验证 | 能否用边界测试证明承诺，而不只运行 happy path？ |
| 复盘 | 能否写出一次误解、证据、修正和知识连接？ |

分数低不是失败，它告诉你下一周应该继续使用哪张卡。真正需要避免的是“项目跑起来了，所以设计能力自然会增长”的想法；没有显式分析和复盘，经验很容易只停留在复制目录和试错命令上。

## 9. 常见误区

1. **先建十层目录再想需求**：目录不能替代职责分析。
2. **一个类负责全部流程**：能运行，但任何变化都会修改同一处。
3. **每个名词都做成类**：抽象数量增加，不代表边界更清楚。
4. **到处使用单例和全局变量**：依赖被隐藏，生命周期和测试互相干扰。
5. **头文件包含实现文件**：破坏正常编译边界；模板 `.tpp` 是有明确原因的例外组织方式。
6. **只测试最终输出**：无法定位是解析、算法还是输出层出错。
7. **总结等于抄目录**：没有前提、反例和连接，知识仍是孤立条目。
8. **设计必须一次正确**：设计是提出候选、记录取舍、用变化和测试校正的过程。

从第一周开始，你不需要凭空“像架构师一样思考”。只需要坚持按模板留下可检查的中间结果。随着语言、算法、所有权和并发知识增加，这些模板会逐渐变成你自己的设计习惯。

## 10. 怎样把设计原则变成可验证决定

“低耦合”“高内聚”“依赖抽象”如果没有具体变化场景，就只是口号。每个重要设计决定至少写成下面四列：

| 决定 | 解决的变化或风险 | 新成本 | 验证证据 |
|---|---|---|---|
| 把解析器与算法拆成两个 target | 输入格式变化不应修改核心算法 | 多一个接口和构建边 | 用假解析结果直接测试算法库 |
| 用 `unique_ptr` 返回独占对象 | 调用者必须接管销毁责任 | 对象不能隐式复制 | 编译期拒绝复制，移动后只有一个 owner |
| 引入 Pimpl | 稳定公开头文件并隔离实现依赖 | 间接访问、分配和特殊成员定义 | 修改实现头后下游无需重新编译 |
| 在线程池加入 close | 阻止析构时仍接受新任务 | API 多一个状态和失败路径 | close 后 submit 被拒绝，已接受任务排空并 join |

这张表把“原则”变成可以反驳的工程假设。若验证证据不存在，说明抽象可能只是增加了文件和类；若新成本超过变化收益，应保留更简单的结构。

### 10.1 标准规则、指南和架构经验怎样配合

- C++ working draft/cppreference 用于确认对象生命周期、ODR、模板实例化和标准库契约。
- ISO C++ Core Guidelines 用于检查接口、资源管理、类设计和并发实践，但它是指南，不是语言规范。
- 《A Tour of C++》《C++ Primer》用于补语言和库基础，避免用架构术语掩盖语义不清。
- John Lakos 的大规模 C++ 资料用于理解物理设计、依赖方向和构建成本；具体目录仍应由本项目的变化和发布边界决定。
- 设计模式资料用于给重复结构命名；先证明变化点，再决定是否引入模式。

推荐资料：

- C++ working draft：<https://eel.is/c++draft/>
- cppreference：<https://en.cppreference.com/w/>
- ISO C++ Core Guidelines：<https://isocpp.github.io/CppCoreGuidelines/>
- CMake target 教程：<https://cmake.org/cmake/help/latest/guide/tutorial/>
- [设计模式教程](设计模式教程.md)：在本教程的问题卡和所有权图之后阅读。

资料给出模型，仓库中的真实接口、target、测试和失败路径才是最终证据。每次引用一条原则，都应同时指出它在当前项目中保护了哪个不变量或变化边界。
