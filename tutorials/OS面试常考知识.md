# 操作系统基础与面试复习

> 本教程为 C++ 学习补充进程、调度、虚拟内存、文件系统和 I/O 背景，并整理常见面试问题。它描述的是经典操作系统模型和常见实现，不把 Linux/Windows 惯例写成 C++ 语言保证。

阅读时区分三层：

1. **C++ 抽象机**：例如数据竞争、对象生命周期和 happens-before，由 C++ 标准定义。
2. **操作系统接口**：例如进程、线程、虚拟内存和文件描述符，由平台 API 定义。
3. **硬件实现**：例如页表、TLB、缓存一致性和中断，由体系结构与具体处理器定义。

三层会互相影响，但不能直接等同。学习 C++ 并发时，以 [C++ 并发编程教程](CPP并发编程教程.md) 的语言内存模型为准；本教程帮助解释线程为什么要调度、阻塞和访问共享地址空间。

## 1. 进程与线程

### 1.1 进程的概念

进程可以理解为操作系统管理的一次程序执行及其资源容器。经典教材常把它概括为“资源分配的基本单位”，但这是一种教学模型，不是所有内核都必须采用的术语。一个进程通常拥有虚拟地址空间、打开的文件/句柄、安全凭据和一个或多个可调度执行流；共享库页面、共享内存和内核对象又可能跨进程共享。

PCB（Process Control Block）是抽象名称，真实系统的数据结构可能分散在多个内核对象中。下图列的是常见信息类别，不表示每个字段都只保存一份或采用相同名字：

### 1.2 进程状态转换

```
进程五状态模型：

 New ──接纳──> Ready ──调度──> Running ──退出──> Terminated
                  ↑               │
                  │               ├──抢占/时间片到期──> Ready
                  │               │
                  └──事件完成── Blocked
                                  ↑
                                  └──等待 I/O/锁/事件── Running

状态转换说明：
1. 创建 → 就绪：进程被创建，分配资源
2. 就绪 → 执行：调度程序选中该进程
3. 执行 → 就绪：时间片用完或被抢占
4. 执行 → 阻塞：等待 I/O 或事件
5. 阻塞 → 就绪：I/O 完成或事件发生
6. 执行 → 结束：进程完成任务
```

Blocked 与 Waiting 在许多教材中是同一类状态，不应在“五状态模型”里重复算成两个独立状态。真实内核通常有更细的可中断睡眠、不可中断睡眠、停止、僵尸等状态；面试时先说明使用的是哪种模型，再解释平台扩展。

### 1.3 线程的概念

线程是进程内的一条执行流。主流通用操作系统通常调度内核线程或与之对应的任务，因此教材常称线程为“CPU 调度的基本单位”；用户级线程、协程和混合线程模型会让“谁真正被内核调度”更复杂。线程通常共享进程地址空间和打开资源，同时各自拥有寄存器上下文、栈以及线程局部存储。

```
进程与线程的区别：

┌─────────────────────────────────────────────────────────────┐
│                        对比项                                │
├─────────────┬─────────────────────┬─────────────────────────┤
│    维度      │        进程         │          线程           │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 资源视角     │ 地址空间与 OS 资源容器│ 共享多数进程资源         │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 调度视角     │ 取决于内核任务模型   │ 主流系统通常调度线程     │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 地址空间     │ 独立                │ 共享                    │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 通信方式     │ IPC/共享内存/消息    │ 共享地址空间，需显式同步 │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 创建开销     │ 通常较大            │ 通常较小，非标准保证     │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 切换开销     │ 可能涉及地址空间切换 │ 通常少一些，依平台而定   │
├─────────────┼─────────────────────┼─────────────────────────┤
│ 故障隔离     │ 通常更强            │ 共享地址空间，故障会波及进程│
└─────────────┴─────────────────────┴─────────────────────────┘
```

“线程共享内存，所以通信简单”只说了一半。可达性更直接，但两个线程无同步地冲突访问同一对象会在 C++ 中形成数据竞争和未定义行为；共享越容易，越需要明确所有者、互斥不变量和退出协议。

### 1.4 进程调度算法

```
常见进程调度算法：

1. 先来先服务（FCFS）
   - 按到达顺序执行
   - 简单但可能导致"护航效应"
   - 非抢占式

2. 短作业优先（SJF）
   - 选择估计运行时间最短的进程
   - 在已知/可准确预测服务时间和给定模型下可最小化平均等待时间
   - 可能导致长作业"饥饿"

3. 优先级调度
   - 按优先级选择进程
   - 可能导致低优先级进程"饥饿"
   - 解决：优先级老化

4. 时间片轮转（RR）
   - 每个进程分配固定时间片
   - 时间片用完则重新排队
   - 适合分时系统

   RR 演算（4 进程同时到达，burst：P1=4, P2=3, P3=1, P4=5，时间片 q=2）：
   就绪队列按 P1→P2→P3→P4 轮转，每轮各跑不超过 q：
   ```
   时刻: 0  2  4  5  7  9 10 13
   P1:   ██      (跑0-2,剩2)→(再跑7-9,完)
   P2:      ██   (跑2-4,剩1)→(再跑9-10,完)
   P3:         █ (跑4-5,剩0,完)
   P4:           ██     (跑5-7,剩3)→(跑10-13,完)
   甘特: P1 P1 P2 P2 P3 P4 P4 P1 P1 P2 P4 P4 P4
   完成时间: P3=5, P1=9, P2=10, P4=13
   ```
   要点：时间片到点就被抢占、排到队尾，等下一轮再跑剩余部分；短进程（P3）能很快完成，体现了"分时、响应快"。注意 RR 的就绪队列是 FIFO，被抢占的进程回到队尾而非队首。

5. 多级反馈队列
   - 多个优先级队列
   - 时间片随优先级降低而增大
   - 综合了多种算法的优点
```

```
多级反馈队列调度示例：

┌─────────────────────────────────────────────────────────────┐
│  队列1（最高优先级）    时间片: 2ms                          │
│  ┌───┬───┬───┬───┬───┐                                      │
│  │ P1│ P2│ P3│...│   │                                      │
│  └───┴───┴───┴───┴───┘                                      │
├─────────────────────────────────────────────────────────────┤
│  队列2（中等优先级）    时间片: 4ms                          │
│  ┌───┬───┬───┬───┬───┐                                      │
│  │ P4│ P5│...│   │   │                                      │
│  └───┴───┴───┴───┴───┘                                      │
├─────────────────────────────────────────────────────────────┤
│  队列3（最低优先级）    时间片: 8ms                          │
│  ┌───┬───┬───┬───┬───┐                                      │
│  │ P6│...│   │   │   │                                      │
│  └───┴───┴───┴───┴───┘                                      │
└─────────────────────────────────────────────────────────────┘

调度规则：
1. 新进程进入队列1
2. 时间片用完未结束，降级到下一队列
3. 高优先级队列非空时，优先调度
```

## 2. 进程同步与互斥

### 2.1 基本概念

```
临界资源与临界区：

临界资源：一次只允许一个进程使用的资源
临界区：访问临界资源的代码段

进入临界区的四个准则：
1. 空闲让进：临界区空闲时，允许进入
2. 忙则等待：临界区忙碌时，必须等待
3. 有限等待：保证请求能在有限时间内进入
4. 让权等待：等待时应释放 CPU
```

这些准则来自经典临界区问题，其中“有限等待”讨论的是饥饿边界，“让权等待”讨论的是阻塞而非持续忙等。C++ 标准 mutex 并不普遍承诺公平性，因此“没有 data race”与“每个线程最终都能拿到锁”是两个不同问题。

把 OS 术语映射到 C++ 时要分清：

| 抽象 | 保存的状态 | 典型用途 | 不能替代什么 |
|---|---|---|---|
| mutex | 所有权/互斥状态 | 保护一组共享不变量 | 不表达“有多少资源可用” |
| condition variable | 不保存业务条件，只负责等待与通知 | 等待受 mutex 保护的谓词 | 通知不能替代谓词，可能虚假唤醒 |
| semaphore | 可用许可数量 | 限流、固定资源池、生产/消费计数 | 不自动保护许可关联的数据结构 |
| atomic | 单个原子对象及其内存序 | 计数、标志、经过证明的状态机 | 不自动维护多个字段的事务不变量 |

例如有界队列通常同时需要“队列内容与关闭状态”的 mutex 不变量、`not_empty/not_full` 谓词以及停止协议。只把计数器改成 atomic，无法保证元素存储、队头队尾和关闭状态作为一个整体一致。

### 2.2 信号量机制

```
信号量类型：

1. 整型信号量
   S: 整数变量
   
   wait(S): while S <= 0; S = S - 1;
   signal(S): S = S + 1;
   
   问题：不满足"让权等待"

2. 记录型信号量
   
   struct Semaphore {
       int value;        // 资源数量
       PCB* queue;       // 等待队列
   };
   
   wait(S):
       S.value--;
       if S.value < 0:
           将进程加入等待队列
           block()
   
   signal(S):
       S.value++;
       if S.value <= 0:
           唤醒等待队列中的进程
           wakeup(P)
```

### 2.3 经典同步问题

#### 生产者-消费者问题

```
问题描述：
• 生产者生产产品放入缓冲区
• 消费者从缓冲区取出产品消费
• 缓冲区大小固定

信号量设置：
• mutex = 1          // 互斥信号量
• empty = n          // 空缓冲区数量
• full = 0           // 满缓冲区数量

生产者：
P(empty)  // 等待空位
P(mutex)  // 获取互斥锁
  放入产品
V(mutex)  // 释放互斥锁
V(full)   // 增加满缓冲区

消费者：
P(full)   // 等待产品
P(mutex)  // 获取互斥锁
  取出产品
V(mutex)  // 释放互斥锁
V(empty)  // 增加空缓冲区

注意：P(empty) 和 P(full) 必须在 P(mutex) 之前，
      否则可能死锁！
```

#### 读者-写者问题

```
问题描述：
• 多个读者可同时读
• 写者必须独占访问
• 读写互斥

读者优先解法：

int readCount = 0;
Semaphore mutex = 1;    // 保护 readCount
Semaphore write = 1;    // 写互斥

读者：
P(mutex)
  readCount++;
  if readCount == 1:
      P(write)          // 第一个读者阻塞写者
V(mutex)

  读取数据

P(mutex)
  readCount--;
  if readCount == 0:
      V(write)          // 最后一个读者释放写者
V(mutex)

写者：
P(write)
  写入数据
V(write)
```

#### 哲学家就餐问题

```
问题描述：
• 5 个哲学家围坐圆桌
• 每两人之间一支筷子
• 需要两支筷子才能就餐

死锁风险解法：
P(左筷子)
P(右筷子)
  就餐
V(右筷子)
V(左筷子)

可能死锁：所有哲学家都拿起左边筷子

解决方案：
1. 最多允许 4 人同时就餐
2. 奇数号先拿左，偶数号先拿右
3. 只有两支筷子都可用时才拿
```

## 3. 死锁

### 3.1 死锁的四个必要条件

```
死锁必要条件（必须同时满足）：

1. 互斥条件
   资源一次只能被一个进程使用

2. 请求与保持条件
   进程持有资源同时请求新资源

3. 不剥夺条件
   已分配资源不能被强制剥夺

4. 循环等待条件
   存在进程资源的循环等待链

┌─────────┐      ┌─────────┐
│ 进程 A  │ ───→ │ 进程 B  │
│ 持有 R1 │      │ 持有 R2 │
│ 等待 R2 │      │ 等待 R1 │
└─────────┘ ←─── └─────────┘
        循环等待
```

### 3.3 银行家算法

```
银行家算法核心思想：
在分配资源前，先判断分配后系统是否处于安全状态。

数据结构：
• Available[]：可用资源向量
• Max[][]：最大需求矩阵
• Allocation[][]：已分配矩阵
• Need[][]：需求矩阵（Need = Max - Allocation）

安全性算法：
1. 初始化 Work = Available, Finish[i] = false
2. 找满足条件的进程 i：
   Finish[i] == false && Need[i] <= Work
3. 找到则：
   Work = Work + Allocation[i]
   Finish[i] = true
   回到步骤 2
4. 若所有 Finish[i] == true，则安全

示例：
进程    Max      Allocation   Need      Available
        A  B     A  B         A  B      A  B
P0      7  5     0  1         7  4      3  3
P1      3  2     2  0         1  2
P2      9  0     3  0         6  0
P3      2  2     2  1         0  1
P4      4  3     0  0         4  3

安全序列：P1 → P3 → P4 → P0 → P2
```

## 4. 内存管理

### 4.1 内存分配方式

```
内存分配方式：

1. 连续分配
   • 单一连续分配：单道程序
   • 固定分区分配：分区大小固定
   • 动态分区分配：按需分配

2. 非连续分配
   • 分页存储
   • 分段存储
   • 段页式存储

动态分区分配算法：

┌─────────────────────────────────────────────────────────────┐
│  首次适应（First Fit）                                       │
│  • 从头查找，第一个够大的空闲区                              │
│  • 简单，开销小                                              │
│  • 可能产生外部碎片                                          │
├─────────────────────────────────────────────────────────────┤
│  最佳适应（Best Fit）                                        │
│  • 找最小的够大空闲区                                        │
│  • 浪费空间最小                                              │
│  • 产生很多小碎片                                            │
├─────────────────────────────────────────────────────────────┤
│  最坏适应（Worst Fit）                                       │
│  • 找最大的空闲区                                            │
│  • 避免产生小碎片                                            │
│  • 大作业可能无法分配                                        │
├─────────────────────────────────────────────────────────────┤
│  邻近适应（Next Fit）                                        │
│  • 从上次分配位置开始查找                                    │
│  • 均匀分配                                                  │
└─────────────────────────────────────────────────────────────┘
```

三种算法用同一空闲区表各分配一次，看差异。空闲区（按地址排序）：`[10, 20, 5, 15]`，请求分配 `12`：

```
First Fit: 从头找第一个 ≥12 → 命中第二个(20)，划出12，剩 8
   剩余空闲: [10, 8, 5, 15]    (从第一个够大的就切，简单快)
Best  Fit: 找最小的 ≥12 → 候选 20(余8) 和 15(余3)，取最小15，划出12，剩 3
   剩余空闲: [10, 20, 5, 3]    (留下更小的碎片 3)
Worst Fit: 找最大的 ≥12 → 20 最大，划出12，剩 8
   剩余空闲: [10, 8, 5, 15]    (与 First Fit 相同，但耗掉了最大的块)
```

差异就在"切哪块"：First 切第一块够大的（20，余8）；Best 切最贴近的（15，余3，产生小碎片）；Worst 切最大的（20，余8，但大块没了）。各自的代价从这个演算就能看出——**Best Fit 倾向产生细小碎片**（如这里的余 3，太小再用不上，是外部碎片）；**Worst Fit 倾向耗尽大块**（把唯一的 20 切了，以后再来大请求就没大块可用）；First Fit 简单但分配点之前的空闲区会越来越碎。这些不是背定义，是演算可见。

> **外部碎片 vs 内部碎片**：这两个词反复出现但从未定义。**外部碎片**=空闲区太碎、单个太小不够用但总和够（如 First Fit 剩的 10+8+5+15，想再分 20 就不行，虽然总和 38 够）——它是"之间"的碎片，靠紧缩(移动)可消除。**内部碎片**=分配出去的块里没用满的部分（如按 4KB 页框分配，某进程只用 3KB，那 1KB 是内部碎片，分出去就回不来，只能靠缩小分配粒度缓解）。

### 4.2 分页存储管理

```
分页存储：

• 将进程逻辑地址空间分成大小相等的页
• 将物理内存分成大小相等的页框
• 页和页框大小相同

地址结构：
┌───────────────────┬───────────────────┐
│    页号 P          │    页内偏移 d      │
│   (高位)          │    (低位)          │
└───────────────────┴───────────────────┘

地址变换：
逻辑地址 → 查页表 → 物理地址

┌───────┐      ┌───────┐      ┌───────┐
│ 页号  │ ──→  │ 页表  │ ──→  │ 页框号│
└───────┘      └───────┘      └───────┘
                          │
                          ▼
                    ┌───────────┐
                    │ 物理地址   │
                    │ = 页框号   │
                    │ × 页大小   │
                    │ + 偏移     │
                    └───────────┘

页表项结构：
┌──────────┬──────────┬──────────┬──────────┐
│  页框号   │ 有效位   │ 访问位   │ 修改位   │
└──────────┴──────────┴──────────┴──────────┘
```

#### 具体演算：一个虚拟地址怎么变成物理地址

只看框图不够，要走一次数值演算才懂。设 32 位虚拟地址、页大小 4KB（2¹² B），则地址拆成：高 20 位 = 页号，低 12 位 = 页内偏移。

```
虚拟地址 0x00012345（32 位）：
  ┌────────────────────┬────────────┐
  │ 页号 P (20 位)       │ 偏移 d (12 位)│
  │   = 0x00012 = 18     │   = 0x345    │
  └────────────────────┴────────────┘

查页表第 18 项 → 假设页框号 = 5
物理地址 = 页框号 × 4096 + 偏移 = 5 × 4096 + 0x345 = 20480 + 837 = 0x5345
        ┌────────────────────┬────────────┐
        │ 页框号 (20 位)       │ 偏移 (12 位)│
        │   = 5                │   = 0x345    │  ← 偏移原样拼回低位
        └────────────────────┴────────────┘
```

关键点：**偏移位不参与查表**，直接原样拼到物理地址低位；查表只决定高位（页框号）。所以页大小决定"页内偏移占多少位"，剩余高位才是页号。

#### TLB：缓存页表查找的结果

每次访存都查内存里的页表会慢一倍（一次访存变两次）。TLB（Translation Lookaside Buffer，页表缓存）是 CPU 内一组硬件条目，缓存最近用过的"页号→页框号"映射。

```
访存时先查 TLB：
  虚拟页号 → 查 TLB
   ├─ 命中（TLB hit）:  直接拿到页框号，无需访存页表，快
   └─ 未命中（TLB miss）: 去内存查页表（"page walk"）
        ├─ 页表项有效位=1: 拿到页框号，填进 TLB，再访存
        └─ 页表项有效位=0: 触发缺页异常（见 §5）
```

TLB 容量小（几十到几百项），但程序访存有局部性（一段时间内集中访问几页），命中率通常 99%+。换进程时旧 TLB 失效，要么全部刷掉（TLB flush），要么靠地址空间标识（ASID）区分不同进程——这叫 TLB shootdown 的反面：多核下让其他核也刷掉对应条目，需发 IPI。TLB 命中率直接影响性能，大页（huge page，如 2MB/页）能减少页表项数、提高 TLB 覆盖率，是大型应用常用优化。

#### 多级页表：为什么能省内存

单级页表有个问题：32 位地址空间有 2²⁰ = 1048576 个页，每页表项 4 字节，**每个进程的页表就要 4MB**——哪怕进程只用了一小段地址空间。因为页表是连续数组，未用的页也得有表项（有效位=0）。

多级页表（二级为例）的思路：**只为实际用到的页建二级表**。

```
单级：连续 4MB 页表，未用页也占项 → 固定 4MB/进程

二级：
  页目录(一级)：2^10 项，每项指向一张二级页表（或标记"不存在"）
  二级页表：每张 2^10 项，4KB

  若进程只用 2 个页（共 8KB）：
   - 页目录只填 1 项，其余 1023 项标"不存在"（不占二级表）
   - 只建 1 张二级表：4KB
   - 总计：页目录 4KB + 1 张二级表 4KB = 8KB，而非 4MB
```

省内存的根因是：**一级页目录里"不存在"的项不分配对应的二级表**。单级表必须为整个地址空间预留，多级表只为"用到的区段"分配。代价是访存时可能要查多级（页目录→二级表），层数多则慢——TLB 正是用来缓解这点。64 位系统地址空间巨大，通常用 4 级甚至 5 级页表，否则单级表根本装不下。

## 5. 虚拟内存

### 5.1 虚拟内存概念

```
虚拟内存：

核心思想：
• 进程不需要全部装入内存即可运行
• 需要时才将页面调入内存
• 暂时不用的页面换出到磁盘

优点：
1. 进程可以比物理内存大
2. 更多的进程可以同时运行
3. 减少内存拷贝开销

实现方式：
• 请求分页
• 请求分段
• 段页式
```

#### 请求分页：缺页中断怎么走

"请求分页"是虚拟内存的核心机制。页表项有**有效位**（present/valid bit）：=1 表示该页在内存，=0 表示不在（在磁盘或还未分配）。CPU 访问一个页时：

```
1. 生成虚拟地址，按 §4.2 拆成页号+偏移，查页表项
2. 有效位 = 1：直接拼出物理地址，访存完成
3. 有效位 = 0 → 触发缺页异常（page fault）：
   a. CPU 陷入内核，切换到内核态，保存现场
   b. OS 查该页的磁盘位置（在换区或可执行文件中）
   c. 若内存没有空闲页框 → 先按置换算法（§5.2）选一页淘汰：
      - 若被淘汰页"修改位=1"（脏页）：写回磁盘
      - 更新被淘汰页的页表项有效位=0
   d. 从磁盘把缺的页读进一个空闲页框
   e. 更新该页表项：页框号=新页框、有效位=1、修改位=0
   f. 恢复现场，重新执行那条触发缺页的指令（这次有效位=1，访存成功）
```

关键认知：**缺页不是错误，是正常控制流**——OS 介入补页后重新执行指令，对程序透明。只是频繁缺页（抖动）会让大部分时间花在换页上（§5.3）。"修改位"决定淘汰时是否要写回磁盘：干净页直接丢弃即可，脏页必须写回——这解释了为什么只读页淘汰廉价。

### 5.2 页面置换算法

```
页面置换算法：

1. 最佳置换（OPT）
   • 置换将来最长时间不使用的页面
   • 理论最优，无法实现
   • 用于评估其他算法

2. 先进先出（FIFO）
   • 置换最早进入的页面
   • 简单，但可能有 Belady 异常
   • Belady 异常：分配页框增多，缺页反而增加

3. 最近最少使用（LRU）
   • 置换最近最长时间未使用的页面
   • 性能接近 OPT
   • 实现需要硬件支持（计数器或栈）

4. 时钟置换（Clock）
   • LRU 的近似实现
   • 使用访问位
   • 指针扫描，遇到访问位=0的置换

5. 最不常用（LFU）
   • 置换访问次数最少的页面
   • 可能保留早期频繁访问但不再需要的页面
```

#### 同一引用串对比四个算法

只看定义看不出差异，要用**同一访问串、同样页框数**演算一遍。取 3 个页框、引用串 `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2`，逐个走 FIFO / LRU / OPT（`✓`=缺页、`✗`=命中）：

```
引用串:  7  0  1  2  0  3  0  4  2  3  0  3  2  1  2      缺页次数
页框数=3
                                                  
FIFO(淘汰最早进入)：
框1:    7  7  7  2  2  2  2  4  4  4  0  0  0  0  0    } 12 次
框2:    -  0  0  0  0  3  3  3  2  2  2  2  2  1  1    }（含 Belady 风险）
框3:    -  -  1  1  1  1  0  0  0  3  3  3  3  3  2    }
缺页:   ✓  ✓  ✓  ✓  ✗  ✓  ✓  ✓  ✓  ✓  ✓  ✗  ✗  ✓  ✓

LRU(淘汰最久没用的)：
框1:    7  7  7  2  2  2  2  4  4  4  0  0  0  1  1    } 10 次
框2:    -  0  0  0  0  0  0  0  0  3  3  3  3  3  3    }
框3:    -  -  1  1  1  3  3  3  2  2  2  2  2  2  2    }
缺页:   ✓  ✓  ✓  ✓  ✗  ✓  ✗  ✓  ✓  ✓  ✓  ✗  ✗  ✓  ✗

OPT(淘汰将来最久不用的，需预知未来)：
框1:    7  7  7  2  2  2  2  2  2  2  2  2  2  2  2    } 8 次
框2:    -  0  0  0  0  0  0  4  4  4  0  0  0  1  1    }（理论下界）
框3:    -  -  1  1  1  3  3  3  3  3  3  3  3  3  3    }
缺页:   ✓  ✓  ✓  ✓  ✗  ✓  ✗  ✓  ✗  ✗  ✓  ✗  ✗  ✓  ✗
```

这条串上 OPT(8) < LRU(10) < FIFO(12)，差距明显。这就是为何要用同一串对比——只讲定义会让人以为差不多。LRU 比 OPT 多 2 次是因为它不知未来，有时淘汰了马上又要用的页；FIFO 更差因为它只看"进入早晚"，完全不顾访问模式。**别因某串上恰好相等就以为算法等价**——换一条串差距会变。

```
Clock（二次机会，近似 LRU）：
  每个页框带访问位；命中时置访问位=1，缺页淘汰时指针扫：
    访问位=1 → 清成 0，指针前进（给一次"二次机会"）
    访问位=0 → 淘汰它，换入新页（新页访问位置 1）
  环形指针把"最近被访问过的页"暂时保留，近似 LRU 但只需一个访问位（硬件已提供）。
```

Clock 的优势是用现有访问位实现，不需计数器或栈，是实际操作系统（如 Linux 的活跃/非活跃链表）常用思路。完整精确的 LRU 需要每次访存都更新次序记录，开销太大，所以真实系统都用 Clock 类近似。

**Belady 异常**：FIFO 有个著名反常——页框数 3→4 时缺页数可能**反而增加**。原因是 FIFO 不满足"栈算法"性质（更多页框时，小页框时刻的页面集合不一定是大页框的子集）。LRU 和 OPT 满足栈性质，更多页框绝不增缺页。面试问"Belady 异常出现在哪个算法"答 FIFO。

### 5.3 抖动现象

```
抖动（Thrashing）：

定义：
• 进程频繁缺页，大部分时间花在换页上
• 系统吞吐量急剧下降

原因：
• 进程分配的页框太少
• 置换算法不当
• 全局置换导致进程间干扰

解决方法：
1. 局部置换策略
2. 工作集模型
3. 缺页率置换

工作集模型：
Working Set = 最近 Δ 时间访问的页面集合

如果 工作集大小 > 分配页框数
   则进程可能抖动
```

### 6.3 磁盘调度算法

```
磁盘访问时间 = 寻道时间 + 旋转延迟 + 传输时间

磁盘调度算法（减少寻道时间）：

1. 先来先服务（FCFS）
   • 按请求顺序处理
   • 公平但效率低

2. 最短寻道时间优先（SSTF）
   • 选择离当前磁头最近的请求
   • 可能导致"饥饿"

3. 扫描算法（SCAN/电梯算法）
   • 磁头单向移动，处理沿途请求
   • 到边界后反向
   • 公平，无饥饿

4. 循环扫描（C-SCAN）
   • 单向扫描，到边界后回到起点
   • 更均匀的等待时间

示例：磁道请求序列 98, 183, 37, 122, 14, 124, 65, 67
      当前位置：53，初始方向：向外

SCAN 执行过程：
53 → 37 → 14 → (0边界) → 65 → 67 → 98 → 122 → 124 → 183

C-SCAN 执行过程：
53 → 37 → 14 → (回到199) → 183 → 124 → 122 → 98 → 67 → 65
```

## 7. I/O 系统

### 7.1 I/O 控制方式

```
I/O 控制方式演进：

1. 程序直接控制
   • CPU 不断查询 I/O 状态
   • CPU 和 I/O 串行工作
   • 效率最低

2. 中断驱动
   • I/O 完成后中断 CPU
   • CPU 和 I/O 并行工作
   • 数据传输仍需 CPU 参与

3. DMA 方式
   • DMA 控制器直接控制数据传输
   • CPU 只需设置参数
   • 适合批量数据传输

4. 通道控制
   • 专门的 I/O 处理机
   • CPU 只需发一条 I/O 指令
   • 效率最高

DMA 工作流程：
┌─────────┐    ┌─────────┐    ┌─────────┐

### 8.3 银行家算法计算

```
问题：判断系统是否安全

T0 时刻资源状态：
进程     Max      Allocation     Need      Available
        A B C     A B C         A B C     A B C
P0      7 5 3     0 1 0         7 4 3     3 3 2
P1      3 2 2     2 0 0         1 2 2
P2      9 0 2     3 0 2         6 0 0
P3      2 2 2     2 1 1         0 1 1
P4      4 3 3     0 0 2         4 3 1

安全性检查（从 Available=(3,3,2) 出发，每步找一个 Need ≤ Work 的进程，执行后回收其 Alloc）：

```
Work = (3,3,2)，所有进程未完成
1. 找 Need ≤ (3,3,2) 的进程：
   P1: Need(1,2,2) ≤ (3,3,2)? Yes → 执行 P1
      Work = (3,3,2) + Alloc(2,0,0) = (5,3,2)
2. 找 Need ≤ (5,3,2)：
   P3: Need(0,1,1) ≤ (5,3,2)? Yes → 执行 P3
      Work = (5,3,2) + Alloc(2,1,1) = (7,4,3)
3. 找 Need ≤ (7,4,3)：
   P0: Need(7,4,3) ≤ (7,4,3)? Yes → 执行 P0
      Work = (7,4,3) + Alloc(0,1,0) = (7,5,3)
   （P4: Need(4,3,1) ≤ (7,5,3)? 也 Yes，选谁都行——安全序列可不唯一）
4. 找 Need ≤ (7,5,3)：
   P2: Need(6,0,0) ≤ (7,5,3)? Yes → 执行 P2
      Work = (7,5,3) + Alloc(3,0,2) = (10,5,5)
5. 找 Need ≤ (10,5,5)：
   P4: Need(4,3,1) ≤ (10,5,5)? Yes → 执行 P4
      Work = (10,5,5) + Alloc(0,0,2) = (10,5,7)
所有进程完成 → 系统安全
```

安全序列：**P1 → P3 → P0 → P2 → P4**（按"第一个满足的"找；若第 3 步先选 P4，则得 P1→P3→P4→P0→P2，同样合法。**安全序列可不唯一，能找到一个就够判安全**）。判定要点：每步 Work 不断增长（执行进程回收它的资源），最终所有进程都能完成即安全；若某步没有任何 Need ≤ Work 的未完成进程，则死锁不安全。

### 8.4 资源请求的银行家判定（示例）

安全检查只判"当前状态"。实际使用是"进程请求资源时，先假装分配，再做安全检查，安全才真分配"。设 P1 请求 (1,0,2)：

```
请求 (1,0,2) ≤ Need(P1)=(1,2,2)? Yes
请求 (1,0,2) ≤ Available(3,3,2)? Yes
试探分配：Available = (3,3,2)-(1,0,2) = (2,3,0)
          Alloc(P1) = (2,0,0)+(1,0,2) = (3,0,2)
          Need(P1)  = (1,2,2)-(1,0,2) = (0,2,0)
做 §8.3 的安全性检查：若试探后仍存在安全序列 → 真正分配；否则拒绝，进程等待。
```

这条流程把"请求—检查—分配/拒绝"讲全：请求不能超过自己的 Need，也不能超过系统 Available；满足这两条才试探分配并重判安全性。安全才落实，不安全就回滚、让请求者等待——这正是银行家算法"在分配前保证不进入不安全状态"的核心。

## 面试高频问题汇总

### 进程与线程

```
Q1: 进程和线程的区别？
A: 进程是资源分配单位，线程是调度单位。
   进程有独立地址空间，线程共享进程资源。
   进程创建/切换开销大，线程开销小。

Q2: 为什么线程切换比进程快？
A: 同一进程内切换通常不需要更换地址空间，
   因而可能减少页表/TLB 和资源上下文成本；
   但实际开销受内核、硬件标签、缓存命中和调度路径影响，不能写成固定结论。

Q3: 多进程 vs 多线程的选择？
A: 先比较故障隔离、安全边界、共享数据量、部署方式和通信协议。
   多进程通常隔离更强，多线程共享更直接；性能必须结合工作负载测量，
   不能简单写成“要性能就用线程”。
```

### 同步与死锁

```
Q4: 什么是死锁？如何避免？
A: 死锁是多个进程互相等待对方资源导致都无法继续。
   可通过固定加锁顺序、一次取得多个锁、缩短持有期或消息传递破坏等待环；
   银行家算法属于已知最大需求模型下的避免算法，不是通用动态检测方案。

Q5: 信号量和互斥锁的区别？
A: 互斥锁：二值，用于互斥
   信号量：多值，可用于互斥和同步

Q6: 自旋锁 vs 互斥锁？
A: 自旋锁：忙等待，适合短时间持有
   互斥锁：阻塞等待，适合长时间持有
```

### 内存管理

```
Q7: 分页和分段的区别？
A: 分页：固定大小，无逻辑意义，有内部碎片
   分段：可变大小，有逻辑意义，有外部碎片

Q8: 虚拟内存的作用？
A: 1. 为进程提供隔离的虚拟地址空间和权限保护
   2. 通过按需映射、共享页和换页提高物理内存利用率
   3. 允许虚拟地址空间大于当前驻留物理内存，但仍受地址空间、提交和后备存储限制

Q9: 常见页面置换算法？
A: OPT（最优）、FIFO、LRU、Clock、LFU
   精确 LRU 的维护成本可能很高，实际系统常使用 Clock、近似 LRU、工作集或多队列策略。
```

### I/O 系统

```
Q10: DMA 的工作原理？
A: DMA 控制器直接管理内存和外设间的数据传输，
    CPU 只需初始化参数，完成后中断通知。

Q11: 阻塞 I/O vs 非阻塞 I/O？
A: 阻塞：I/O 完成前进程阻塞
    非阻塞：I/O 未完成立即返回，进程可继续执行
```
