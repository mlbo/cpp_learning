# 设计模式教程：从问题、约束到现代 C++ 实现

> 本教程系统讲解 23 种经典设计模式，但不把模式当作必须套用的类图。每一节都应先识别变化点、所有权和失败方式，再判断模式带来的间接层是否值得。

建议先掌握 [C++ 基础学习教程](CPP基础学习教程.md) 中的类、虚函数、智能指针和 Lambda，并使用 [C++ 项目组织与设计教程](C++项目组织与设计教程.md) 的问题卡与接口卡描述需求。模式解决的是反复出现的设计压力，不是用来替代对象不变量、RAII、测试和简单函数组合。

> **多态前置**：本教程大量使用 `virtual` 与 `override`（如 78 处 `override`），但默认读者已懂多态机制。若对"虚函数表（vtable）、虚析构为何必须 virtual、`override` 检查什么、对象切片"还不清楚，请先读 [C++ 类与对象核心教程 §6 多态与虚函数](C++类与对象核心教程.md#6-多态与虚函数)——那里把多态的底层原理讲透后，再回来学设计模式会顺很多。

阅读每个模式时固定回答：

1. 哪个变化会迫使现有代码反复修改？
2. 模式把稳定部分和变化部分分别放在哪里？
3. 谁拥有参与对象，谁只观察，回调能否超过被捕获对象寿命？
4. 新增了哪些间接调用、动态分配、同步或调试成本？
5. 一个函数、值类型、`std::variant` 或模板参数是否已经足够？
6. 怎样通过替换实现、失败注入和生命周期测试证明边界有效？

GoF 模式描述的是设计词汇，不是 C++ 标准规则。示例会优先使用 RAII、值语义和显式所有权；涉及并发时仍要遵守 [C++ 并发编程教程](CPP并发编程教程.md) 中的数据竞争与关闭协议。

### 1.2 设计原则（SOLID）

| 原则 | 全称 | 含义 |
|------|------|------|
| **S** | Single Responsibility | 单一职责：一个类只负责一件事 |
| **O** | Open/Closed | 开闭原则：对扩展开放，对修改关闭 |
| **L** | Liskov Substitution | 里氏替换：子类可以替换父类 |
| **I** | Interface Segregation | 接口隔离：接口要小而专一 |
| **D** | Dependency Inversion | 依赖倒置：依赖抽象而非具体 |

这张表只是索引，不能按字面机械执行：

- **SRP** 不是“一个类只能有一个方法”，而是把因不同参与者或变化原因而修改的职责分开。
- **OCP** 不要求预测所有未来扩展；只有变化方向已经反复出现时，稳定接口和扩展点才值得成本。
- **LSP** 是行为契约：派生类型不能加强前置条件、削弱后置条件或破坏基类不变量，仅仅“能用基类指针调用”并不够。
- **ISP** 保护调用者不依赖无关能力；拆得过细也会产生大量胶水接口，应围绕真实用例划分。
- **DIP** 要让高层策略不被低层细节牵着修改，依赖注入只是实现手段之一，不需要给每个类都创建一个抽象基类。

判断原则是否改善设计，要用变化实验：替换存储、增加一种输出、注入失败或加入测试替身时，需要修改哪些模块？如果引入接口后修改面反而更大，说明抽象边界选错了。

## 2. 创建型模式

### 2.1 单例模式（面试必考）

**核心思想**：确保一个类只有一个实例，并提供全局访问点。

#### 懒汉式（线程不安全）

```cpp
#include <iostream>

class SingletonLazy {
public:
    static SingletonLazy* getInstance() {
        if (instance_ == nullptr) {
            instance_ = new SingletonLazy();
        }
        return instance_;
    }
    
    void doSomething() { std::cout << "Singleton working\n"; }
    
private:
    SingletonLazy() = default;
    ~SingletonLazy() = default;
    SingletonLazy(const SingletonLazy&) = delete;
    SingletonLazy& operator=(const SingletonLazy&) = delete;
    
    static SingletonLazy* instance_;
};

SingletonLazy* SingletonLazy::instance_ = nullptr;
```

#### 双重检查锁定陷阱

不要把“第一次读取普通指针不加锁、第二次读取加锁”的代码称为线程安全。未加锁读取与另一个线程的写入冲突，会形成数据竞争；第二次检查无法追溯修复第一次检查。正确实现需要原子发布和严格的内存序推理，但在 C++11 以后，函数局部静态对象通常更简单、更容易审查。

如果对象需要显式销毁顺序、测试替身或每个测试独立实例，更好的设计往往不是全局单例，而是由上层 owner 构造普通对象并通过引用传入。单例解决“唯一访问点”，却同时引入隐藏依赖、全局生命周期和测试隔离成本。

#### Meyers 单例（C++11 推荐）

```cpp
#include <iostream>

class SingletonMeyers {
public:
    static SingletonMeyers& getInstance() {
        static SingletonMeyers instance;  // C++11 保证并发初始化只成功一次
        return instance;
    }
    
    void doSomething() { std::cout << "Meyers Singleton\n"; }
    
private:
    SingletonMeyers() = default;
    ~SingletonMeyers() = default;
    SingletonMeyers(const SingletonMeyers&) = delete;
    SingletonMeyers& operator=(const SingletonMeyers&) = delete;
};

// 使用
// SingletonMeyers::getInstance().doSomething();
```

C++11 保证的是函数局部静态对象的初始化协调，不是单例所有成员函数都自动线程安全。如果对象内部有可变共享状态，还要单独定义 mutex、atomic 或线程封闭策略。

#### 面试要点

```
常见问题：
1. 单例模式的线程安全实现？
   答：简单进程内单例优先 Meyers 单例；需要显式生命周期时由上层 owner 管理。不要复制基于普通指针的双重检查锁定。

2. 单例模式的内存泄漏问题？
   答：Meyers 单例在正常程序终止时自动析构；若需要可控的销毁顺序，应由上层 owner 显式管理生命周期

3. 如何防止反射破坏单例？
   答：C++ 无反射机制，主要防止拷贝构造

4. 单例模式的缺点？
   答：全局状态、难以测试、违反单一职责
```

### 2.2 工厂方法模式

**核心思想**：定义一个创建对象的接口，让子类决定实例化哪个类。

```cpp
#include <iostream>
#include <memory>
#include <string>

// 产品接口
class Product {
public:
    virtual ~Product() = default;
    virtual std::string getName() const = 0;
};

// 具体产品 A
class ConcreteProductA : public Product {
public:
    std::string getName() const override { return "Product A"; }
};

// 具体产品 B
class ConcreteProductB : public Product {
public:
    std::string getName() const override { return "Product B"; }
};

// 工厂接口
class Factory {
public:
    virtual ~Factory() = default;
    virtual std::unique_ptr<Product> createProduct() = 0;
};

// 具体工厂 A
class ConcreteFactoryA : public Factory {
public:
    std::unique_ptr<Product> createProduct() override {
        return std::make_unique<ConcreteProductA>();
    }
};

// 具体工厂 B
class ConcreteFactoryB : public Factory {
public:
    std::unique_ptr<Product> createProduct() override {
        return std::make_unique<ConcreteProductB>();
    }
};

// 使用示例
void factoryDemo() {
    std::unique_ptr<Factory> factoryA = std::make_unique<ConcreteFactoryA>();
    auto productA = factoryA->createProduct();
    std::cout << productA->getName() << "\n";  // Product A
    
    std::unique_ptr<Factory> factoryB = std::make_unique<ConcreteFactoryB>();
    auto productB = factoryB->createProduct();
    std::cout << productB->getName() << "\n";  // Product B
}
```

#### 简单工厂（变体）

下面是延续上一个围栏中 `Product`、`ConcreteProductA` 和 `ConcreteProductB` 的上下文片段：

```cpp
enum class ProductType { A, B };

class SimpleFactory {
public:
    static std::unique_ptr<Product> create(ProductType type) {
        switch (type) {
            case ProductType::A:
                return std::make_unique<ConcreteProductA>();
            case ProductType::B:
                return std::make_unique<ConcreteProductB>();
        }
        return nullptr;
    }
};

// 使用
// auto product = SimpleFactory::create(ProductType::A);
```

### 2.3 抽象工厂模式

**核心思想**：创建相关或依赖对象的家族，而无需指定具体类。

```cpp
#include <iostream>
#include <memory>
#include <string>

// 产品家族：按钮
class Button {
public:
    virtual ~Button() = default;
    virtual void render() = 0;
};

class WindowsButton : public Button {
public:
    void render() override { std::cout << "Windows Button\n"; }
};

class MacOSButton : public Button {
public:
    void render() override { std::cout << "macOS Button\n"; }
};

// 产品家族：文本框
class TextBox {
public:
    virtual ~TextBox() = default;
    virtual void render() = 0;
};

class WindowsTextBox : public TextBox {
public:
    void render() override { std::cout << "Windows TextBox\n"; }
};

class MacOSTextBox : public TextBox {
public:
    void render() override { std::cout << "macOS TextBox\n"; }
};

// 抽象工厂
class GUIFactory {
public:
    virtual ~GUIFactory() = default;
    virtual std::unique_ptr<Button> createButton() = 0;
    virtual std::unique_ptr<TextBox> createTextBox() = 0;
};

// Windows 工厂
class WindowsFactory : public GUIFactory {
public:
    std::unique_ptr<Button> createButton() override {
        return std::make_unique<WindowsButton>();
    }
    std::unique_ptr<TextBox> createTextBox() override {
        return std::make_unique<WindowsTextBox>();
    }
};

// macOS 工厂
class MacOSFactory : public GUIFactory {
public:
    std::unique_ptr<Button> createButton() override {
        return std::make_unique<MacOSButton>();
    }
    std::unique_ptr<TextBox> createTextBox() override {
        return std::make_unique<MacOSTextBox>();
    }
};

// 客户端代码
void renderUI(GUIFactory& factory) {
    auto button = factory.createButton();
    auto textBox = factory.createTextBox();
    
    button->render();
    textBox->render();
}
```

### 2.4 建造者模式

**核心思想**：将复杂对象的构建与表示分离，使得同样的构建过程可以创建不同的表示。

```cpp
#include <iostream>
#include <memory>
#include <string>

// 复杂产品
class Computer {
public:
    std::string cpu;
    std::string ram;
    std::string storage;
    std::string gpu;
    
    void show() {
        std::cout << "Computer: CPU=" << cpu 
                  << ", RAM=" << ram
                  << ", Storage=" << storage
                  << ", GPU=" << gpu << "\n";
    }
};

// 建造者
class ComputerBuilder {
public:
    ComputerBuilder& setCPU(const std::string& cpu) {
        computer_.cpu = cpu;
        return *this;
    }
    
    ComputerBuilder& setRAM(const std::string& ram) {
        computer_.ram = ram;
        return *this;
    }
    
    ComputerBuilder& setStorage(const std::string& storage) {
        computer_.storage = storage;
        return *this;
    }
    
    ComputerBuilder& setGPU(const std::string& gpu) {
        computer_.gpu = gpu;
        return *this;
    }
    
    Computer build() { return std::move(computer_); }
    
private:
    Computer computer_;
};

// 使用（链式调用）
void builderDemo() {
    Computer computer = ComputerBuilder()
        .setCPU("Intel i9")
        .setRAM("32GB DDR5")
        .setStorage("1TB NVMe SSD")
        .setGPU("NVIDIA RTX 4090")
        .build();
    
    computer.show();
}
```

### 2.5 原型模式

**核心思想**：通过复制现有对象来创建新对象。

```cpp
#include <iostream>
#include <memory>
#include <string>

class Prototype {
public:
    virtual ~Prototype() = default;
    virtual std::unique_ptr<Prototype> clone() const = 0;
    virtual void show() const = 0;
};

class ConcretePrototype : public Prototype {
public:
    ConcretePrototype(const std::string& name, int value) 
        : name_(name), value_(value) {}
    
    // 拷贝构造实现克隆
    std::unique_ptr<Prototype> clone() const override {
        return std::make_unique<ConcretePrototype>(*this);
    }
    
    void show() const override {
        std::cout << "Prototype: " << name_ << ", " << value_ << "\n";
    }
    
private:
    std::string name_;
    int value_;
};

void prototypeDemo() {
    auto original = std::make_unique<ConcretePrototype>("Original", 100);
    auto clone = original->clone();
    
    original->show();
    clone->show();
}
```

#### 创建型模式怎样选

| 变化压力 | 优先候选 | 关键代价与检查 |
|---|---|---|
| 需要一个进程内访问点 | Singleton | 隐藏依赖和全局生命周期；先考虑普通 owner + 注入 |
| 由子类型决定创建哪一种产品 | Factory Method | 增加继承层次；产品变化方向要稳定 |
| 必须成套创建兼容产品 | Abstract Factory | 新增产品种类会修改所有工厂接口 |
| 构造步骤多且中间状态需要约束 | Builder | Builder 自身也要维护必填字段和失败契约 |
| 运行时复制已有配置 | Prototype | 深/浅复制、身份和外部资源语义必须明确 |

先问“直接构造函数、具名工厂函数或聚合初始化是否足够”。只有对象创建规则反复变化、调用者不应知道具体类型时，创建型模式的间接层才产生净收益。

## 3. 结构型模式

### 3.1 适配器模式（面试高频）

**核心思想**：将一个类的接口转换成客户期望的另一个接口。

```cpp
#include <iostream>
#include <memory>

// 旧接口
class OldSystem {
public:
    void oldMethod() {
        std::cout << "Old system method\n";
    }
};

// 新接口
class NewInterface {
public:
    virtual ~NewInterface() = default;
    virtual void newMethod() = 0;
};

// 适配器（类适配器：多重继承）
class ClassAdapter : public OldSystem, public NewInterface {
public:
    void newMethod() override {
        oldMethod();  // 调用旧方法
    }
};

// 适配器（对象适配器：组合）
class ObjectAdapter : public NewInterface {
public:
    ObjectAdapter(std::unique_ptr<OldSystem> oldSystem)
        : oldSystem_(std::move(oldSystem)) {}
    
    void newMethod() override {
        oldSystem_->oldMethod();
    }
    
private:
    std::unique_ptr<OldSystem> oldSystem_;
};

void adapterDemo() {
    // 类适配器
    NewInterface* adapter1 = new ClassAdapter();
    adapter1->newMethod();
    delete adapter1;
    
    // 对象适配器
    auto oldSystem = std::make_unique<OldSystem>();
    NewInterface* adapter2 = new ObjectAdapter(std::move(oldSystem));
    adapter2->newMethod();
    delete adapter2;
}
```

#### 面试要点

```
类适配器 vs 对象适配器：

类适配器：
- 使用多重继承
- 无法适配子类
- 效率稍高

对象适配器：
- 使用组合
- 可以适配子类
- 更灵活（推荐）
```

### 3.2 装饰器模式

**核心思想**：动态地给对象添加额外的职责。

```cpp
#include <iostream>
#include <memory>
#include <string>

// 组件接口
class Coffee {
public:
    virtual ~Coffee() = default;
    virtual std::string getDescription() const = 0;
    virtual double getCost() const = 0;
};

// 基础组件
class SimpleCoffee : public Coffee {
public:
    std::string getDescription() const override { return "Simple coffee"; }
    double getCost() const override { return 10.0; }
};

// 装饰器基类
class CoffeeDecorator : public Coffee {
public:
    CoffeeDecorator(std::unique_ptr<Coffee> coffee)
        : coffee_(std::move(coffee)) {}
    
protected:
    std::unique_ptr<Coffee> coffee_;
};

// 具体装饰器：牛奶
class MilkDecorator : public CoffeeDecorator {
public:
    using CoffeeDecorator::CoffeeDecorator;
    
    std::string getDescription() const override {
        return coffee_->getDescription() + ", milk";
    }
    
    double getCost() const override {
        return coffee_->getCost() + 2.0;
    }
};

// 具体装饰器：糖
class SugarDecorator : public CoffeeDecorator {
public:
    using CoffeeDecorator::CoffeeDecorator;
    
    std::string getDescription() const override {
        return coffee_->getDescription() + ", sugar";
    }
    
    double getCost() const override {
        return coffee_->getCost() + 1.0;
    }
};

void decoratorDemo() {
    std::unique_ptr<Coffee> coffee = std::make_unique<SimpleCoffee>();
    coffee = std::make_unique<MilkDecorator>(std::move(coffee));
    coffee = std::make_unique<SugarDecorator>(std::move(coffee));
    
    std::cout << coffee->getDescription() << "\n";  // Simple coffee, milk, sugar
    std::cout << "Cost: " << coffee->getCost() << "\n";  // 13
}
```

### 3.3 代理模式

**核心思想**：为其他对象提供代理以控制对这个对象的访问。

```cpp
#include <iostream>
#include <memory>
#include <string>

// 主题接口
class Image {
public:
    virtual ~Image() = default;
    virtual void display() = 0;
};

// 真实主题
class RealImage : public Image {
public:
    RealImage(const std::string& filename) : filename_(filename) {
        loadFromDisk();
    }
    
    void display() override {
        std::cout << "Displaying " << filename_ << "\n";
    }
    
private:
    void loadFromDisk() {
        std::cout << "Loading " << filename_ << " from disk\n";
    }
    
    std::string filename_;
};

// 代理
class ImageProxy : public Image {
public:
    ImageProxy(const std::string& filename) : filename_(filename) {}
    
    void display() override {
        if (!realImage_) {
            realImage_ = std::make_unique<RealImage>(filename_);
        }
        realImage_->display();
    }
    
private:
    std::string filename_;
    std::unique_ptr<RealImage> realImage_;
};

void proxyDemo() {
    // 使用代理延迟加载
    ImageProxy proxy("photo.jpg");
    
    std::cout << "Image created but not loaded yet\n";
    
    // 真正使用时才加载
    proxy.display();
    proxy.display();  // 第二次不会重新加载
}
```

#### 代理类型

```
代理模式分类：

1. 虚拟代理：延迟加载（如上例）
2. 保护代理：控制访问权限
3. 远程代理：代表远程对象
4. 智能引用：自动管理资源
```

### 3.4 外观模式

**核心思想**：为子系统中的一组接口提供一个一致的界面。

```cpp
#include <iostream>
#include <string>

// 子系统
class CPU {
public:
    void start() { std::cout << "CPU started\n"; }
    void shutdown() { std::cout << "CPU shutdown\n"; }
};

class Memory {
public:
    void load() { std::cout << "Memory loaded\n"; }
    void free() { std::cout << "Memory freed\n"; }
};

class HardDrive {
public:
    void read() { std::cout << "HardDrive reading\n"; }
```

### 3.7 享元模式

**核心思想**：运用共享技术有效地支持大量细粒度的对象。

```cpp
#include <iostream>
#include <memory>
#include <unordered_map>
#include <string>
#include <vector>

class TreeType {
public:
    TreeType(const std::string& name, const std::string& color, 
             const std::string& texture)
        : name_(name), color_(color), texture_(texture) {}

    std::string name_;
    std::string color_;
    std::string texture_;

        const std::string& name, 
        const std::string& color,

    {

        auto it = treeTypes_.find(key);
        if (it != treeTypes_.end()) {
            return it->second;
        }

        treeTypes_[key] = treeType;
        return treeType;
    }

    static std::unordered_map<std::string, std::shared_ptr<TreeType>> treeTypes_;

// 上下文：外在状态

    std::shared_ptr<TreeType> type_;

        forest.emplace_back(i * 10, i * 20, oakType);
        forest.emplace_back(i * 10 + 5, i * 20 + 5, pineType);
```

#### 结构型模式怎样选

| 目标 | 优先候选 | 不要混淆 |
|---|---|---|
| 让旧接口满足新调用协议 | Adapter | 它改变接口，不负责访问控制 |
| 运行时叠加职责 | Decorator | 与 Proxy 的访问控制/延迟目的不同 |
| 控制访问、缓存、远程或延迟创建 | Proxy | 代理必须保持被代理接口契约 |
| 给复杂子系统一个稳定入口 | Facade | 外观不是禁止高级调用者访问底层 |
| 独立扩展抽象与实现维度 | Bridge | 只有两条变化轴都真实存在时才值得 |
| 统一处理叶子和组合对象 | Composite | 树所有权、父指针和环必须定义 |
| 共享大量不可变内在状态 | Flyweight | 外在状态不能误放进共享对象；并发访问仍需契约 |

现代 C++ 中，组合和值语义常比深继承层次更简单。结构型模式的核心是依赖方向和对象关系，不是类数量。

### 4.1 策略模式（面试高频）

**核心思想**：定义一系列算法，把它们封装起来，并使它们可以相互替换。

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <algorithm>
#include <functional>

// 策略接口
class SortStrategy {
public:
    virtual ~SortStrategy() = default;
    virtual void sort(std::vector<int>& data) = 0;
};

// 具体策略：快速排序
class QuickSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) override {
        std::cout << "Quick sort\n";
        std::sort(data.begin(), data.end());
    }
};

// 具体策略：冒泡排序
class BubbleSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) override {
        std::cout << "Bubble sort\n";
        for (size_t i = 0; i < data.size(); ++i) {
            for (size_t j = 0; j < data.size() - i - 1; ++j) {
                if (data[j] > data[j + 1]) {
                    std::swap(data[j], data[j + 1]);
                }
            }
        }
    }
};

// 上下文
class Sorter {
public:
    void setStrategy(std::unique_ptr<SortStrategy> strategy) {
        strategy_ = std::move(strategy);
    }
    
    void sort(std::vector<int>& data) {
        if (strategy_) {
            strategy_->sort(data);
        }
    }
    
private:
    std::unique_ptr<SortStrategy> strategy_;
};

// C++11 函数式实现
class SorterFunctional {
public:
    using SortFunction = std::function<void(std::vector<int>&)>;
    
    void setStrategy(SortFunction strategy) {
        strategy_ = std::move(strategy);
    }
    
    void sort(std::vector<int>& data) {
        if (strategy_) {
            strategy_(data);
        }
    }
    
private:
    SortFunction strategy_;
};
```

### 4.2 观察者模式（面试高频）

**核心思想**：定义对象间的一对多依赖，当一个对象改变状态，所有依赖者都会收到通知。

```cpp
#include <iostream>
#include <algorithm>
#include <cstddef>
#include <memory>
#include <vector>
#include <string>
#include <functional>
#include <utility>

// 观察者接口
class Observer {
public:
    virtual ~Observer() = default;
    virtual void update(const std::string& message) = 0;
};

// 具体观察者
class ConcreteObserver : public Observer {
public:
    ConcreteObserver(const std::string& name) : name_(name) {}
    
    void update(const std::string& message) override {
        std::cout << name_ << " received: " << message << "\n";
    }
    
private:
    std::string name_;
};

// 主题
class Subject {
public:
    void attach(const std::shared_ptr<Observer>& observer) {
        observers_.push_back(observer);
    }
    
    void detach(const std::shared_ptr<Observer>& observer) {
        observers_.erase(
            std::remove_if(
                observers_.begin(), observers_.end(),
                [&observer](const std::weak_ptr<Observer>& candidate) {
                    const auto current = candidate.lock();
                    return !current || current == observer;
                }),
            observers_.end()
        );
    }
    
    void notify(const std::string& message) {
        observers_.erase(
            std::remove_if(
                observers_.begin(), observers_.end(),
                [](const std::weak_ptr<Observer>& observer) {
                    return observer.expired();
                }),
            observers_.end());

        std::vector<std::shared_ptr<Observer>> snapshot;
        for (const auto& observer : observers_) {
            if (auto obs = observer.lock()) {
                snapshot.push_back(std::move(obs));
            }
        }
        for (const auto& observer : snapshot) {
            observer->update(message);
        }
    }
    
private:
    std::vector<std::weak_ptr<Observer>> observers_;
};

// C++11 函数式实现
class SubjectFunctional {
public:
    using Callback = std::function<void(const std::string&)>;
    
    std::size_t subscribe(Callback callback) {
        const std::size_t id = next_id_++;
        callbacks_.push_back({id, std::move(callback)});
        return id;
    }
    
    void unsubscribe(std::size_t id) {
        callbacks_.erase(
            std::remove_if(
                callbacks_.begin(), callbacks_.end(),
                [id](const Entry& entry) { return entry.id == id; }),
            callbacks_.end());
    }
    
    void notify(const std::string& message) {
        const auto snapshot = callbacks_;
        for (const auto& entry : snapshot) {
            entry.callback(message);
        }
    }
    
private:
    struct Entry {
        std::size_t id;
        Callback callback;
    };

    std::size_t next_id_{0};
    std::vector<Entry> callbacks_;
};

void observerDemo() {
    Subject subject;
    
    auto observer1 = std::make_shared<ConcreteObserver>("Observer 1");
    auto observer2 = std::make_shared<ConcreteObserver>("Observer 2");
    
    subject.attach(observer1);
    subject.attach(observer2);
    
    subject.notify("Hello observers!");
    
    // 函数式版本
    SubjectFunctional subjFunc;
    const std::size_t id = subjFunc.subscribe([](const std::string& msg) {
        std::cout << "Lambda received: " << msg << "\n";
    });
    
    subjFunc.notify("Hello lambda!");
    subjFunc.unsubscribe(id);
}
```

这里用 `weak_ptr` 保存观察者，表示主题不延长观察者寿命；`notify` 先清理已过期项，再 `lock()` 存活观察者并放入快照。快照有两个作用：保证一次通知期间对象仍存活，并避免回调中的订阅/退订直接破坏当前遍历。这也定义了本例的重入语义：通知已开始后才退订的观察者仍在当前快照中，退订只影响后续通知。函数式版本使用单调递增 token，而不是把 `vector` 下标当永久订阅 ID；删除一个元素后，其余元素下标会变化。

这仍不是完整的并发观察者。若多个线程同时订阅、退订和通知，需要为订阅表定义 mutex 与重入策略；若回调可能阻塞或抛异常，还要规定是串行传播、隔离失败还是调度到执行器。模式名称不能替代这些协议。

### 4.4 迭代器模式

**核心思想**：提供一种方法顺序访问聚合对象中的元素，而不暴露其内部表示。

```cpp
#include <iostream>
#include <cstddef>
#include <memory>
#include <utility>
#include <vector>
#include <string>

template<typename T>
class Iterator {
public:
    virtual ~Iterator() = default;
    virtual bool hasNext() = 0;
    virtual T next() = 0;
};

template<typename T>
class Container {
public:
    virtual ~Container() = default;
    virtual std::unique_ptr<Iterator<T>> createIterator() = 0;
};

class NameRepository : public Container<T> {
public:
    NameRepository(std::vector<T> names) : names_(std::move(names)) {}
    
    std::unique_ptr<Iterator<T>> createIterator() override {
        return std::make_unique<NameIterator>(this);
    }
    
    const std::vector<T>& getNames() const { return names_; }

    std::vector<T> names_;
    
    class NameIterator : public Iterator<T> {
    public:
        NameIterator(NameRepository* repo) : repo_(repo) {}
        
        bool hasNext() override {
            return index_ < repo_->getNames().size();
        }
        
        T next() override {
            if (hasNext()) {
                return repo_->getNames()[index_++];
            }
            return T();
        }
        
    private:
        NameRepository* repo_;
        std::size_t index_ = 0;
    };
};

void iteratorDemo() {
```

### 4.6 责任链模式

**核心思想**：使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合。

```cpp
#include <iostream>
#include <memory>
#include <string>

class Handler {
public:
    virtual ~Handler() = default;
    
    Handler* setNext(Handler* next) {
        next_ = next;
        return next;
    }
    
    virtual std::string handle(const std::string& request) {
        if (next_) {
            return next_->handle(request);
        }
        return "Request unhandled";
    }
    
protected:
    Handler* next_ = nullptr;
};

class MonkeyHandler : public Handler {
public:
    std::string handle(const std::string& request) override {
        if (request == "Banana") {
            return "Monkey: I'll eat the " + request;
        }
        return Handler::handle(request);
    }
};

class SquirrelHandler : public Handler {
public:
    std::string handle(const std::string& request) override {
        if (request == "Nut") {
            return "Squirrel: I'll eat the " + request;
        }
        return Handler::handle(request);
    }
};

class DogHandler : public Handler {
public:
    std::string handle(const std::string& request) override {
        if (request == "Meat") {
            return "Dog: I'll eat the " + request;
        }
        return Handler::handle(request);
    }
};

void chainOfResponsibilityDemo() {
    MonkeyHandler monkey;
    SquirrelHandler squirrel;
    DogHandler dog;
    
    monkey.setNext(&squirrel)->setNext(&dog);
    
    std::cout << monkey.handle("Nut") << "\n";
    std::cout << monkey.handle("Banana") << "\n";
    std::cout << monkey.handle("Meat") << "\n";
    std::cout << monkey.handle("Coffee") << "\n";
}
```

### 4.7 状态模式

**核心思想**：允许对象在其内部状态改变时改变其行为。

```cpp
#include <iostream>
#include <memory>
#include <string>

class State;

class Context {
public:
    Context();
    
    void setState(std::unique_ptr<State> state);
    void request();
    
private:
    std::unique_ptr<State> state_;
};

class State {
public:
    virtual ~State() = default;
    virtual void handle(Context& context) = 0;
    virtual std::string name() const = 0;
};

class ConcreteStateA : public State {
public:
    void handle(Context& context) override;
    std::string name() const override { return "State A"; }
};

class ConcreteStateB : public State {
public:
    void handle(Context& context) override;
    std::string name() const override { return "State B"; }
};

Context::Context() : state_(std::make_unique<ConcreteStateA>()) {}

void Context::setState(std::unique_ptr<State> state) {
    std::cout << "Changing from " << state_->name() 
              << " to " << state->name() << "\n";
    state_ = std::move(state);
}

void Context::request() {
    state_->handle(*this);
}

void ConcreteStateA::handle(Context& context) {
    std::cout << "Handling in State A\n";
    context.setState(std::make_unique<ConcreteStateB>());
}

void ConcreteStateB::handle(Context& context) {
    std::cout << "Handling in State B\n";
    context.setState(std::make_unique<ConcreteStateA>());
}

void stateDemo() {
    Context context;
    
    context.request();  // A -> B
    context.request();  // B -> A
    context.request();  // A -> B
}
```

### 4.8 备忘录模式

**要解决的问题**：对象需要撤销或恢复，但调用者不应直接修改对象内部不变量。备忘录把“可恢复状态”封装成值，由原对象负责创建和验证恢复。

下面是核心接口片段：

```cpp
#include <cstddef>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

struct EditorSnapshot {
    std::string text;
    std::size_t cursor;
};

class Editor {
public:
    EditorSnapshot snapshot() const {
        return {text_, cursor_};
    }

    void restore(EditorSnapshot snapshot) {
        if (snapshot.cursor > snapshot.text.size()) {
            throw std::invalid_argument("cursor outside text");
        }
        text_ = std::move(snapshot.text);
        cursor_ = snapshot.cursor;
    }

    void replace(std::string text, std::size_t cursor) {
        restore({std::move(text), cursor});
    }

private:
    std::string text_;
    std::size_t cursor_{0};
};

class History {
public:
    void save(const Editor& editor) {
        snapshots_.push_back(editor.snapshot());
    }

    bool undo(Editor& editor) {
        if (snapshots_.empty()) {
            return false;
        }
        auto snapshot = snapshots_.back();
        editor.restore(std::move(snapshot));
        snapshots_.pop_back();
        return true;
    }

private:
    std::vector<EditorSnapshot> snapshots_;
};
```

关键不变量是 `cursor <= text.size()`，所以恢复必须回到 `Editor` 内部验证，不能让 `History` 逐字段写私有状态。`undo` 先复制栈顶快照，恢复成功后才弹栈；若复制或恢复抛异常，历史记录仍保留，代价是一次额外复制。完整快照容易理解，但大对象会产生内存成本；实际编辑器常使用命令日志、增量差异或持久化数据结构。快照还可能包含口令、密钥或隐私数据，持久化前必须定义脱敏和加密策略。

### 4.9 中介者模式

**要解决的问题**：多个组件互相直接调用形成网状依赖。中介者把协作流程集中到一个显式协议，让组件只报告事件，不知道其他具体组件。

```cpp
#include <string>
#include <utility>

class DialogMediator {
public:
    virtual ~DialogMediator() = default;
    virtual void changed(const std::string& component,
                         const std::string& value) = 0;
};

class TextBox {
public:
    explicit TextBox(DialogMediator& mediator) : mediator_(mediator) {}

    void edit(std::string value) {
        value_ = std::move(value);
        mediator_.changed("query", value_);
    }

private:
    DialogMediator& mediator_;  // 非拥有引用：mediator 必须更长寿
    std::string value_;
};
```

中介者不是“把所有业务塞进一个大类”。如果每个新组件都要求修改同一个巨大 `if`，中介者已经退化成 God Object；可按用例拆分协调器，或把规则变成策略对象。示例中的引用明确表示不拥有，中介者必须比组件活得更久；异步事件还需要取消订阅、停止和排空协议，不能让回调在组件销毁后继续使用该引用。

### 4.10 访问者模式

**要解决的问题**：元素类型集合相对稳定，但经常新增横跨所有元素的操作。访问者用双分派把新操作集中到一个对象中，代价是新增元素类型时必须修改所有访问者。

```cpp
class Circle;
class Rectangle;

class ShapeVisitor {
public:
    virtual ~ShapeVisitor() = default;
    virtual void visit(const Circle&) = 0;
    virtual void visit(const Rectangle&) = 0;
};

class Shape {
public:
    virtual ~Shape() = default;
    virtual void accept(ShapeVisitor&) const = 0;
};

class Circle final : public Shape {
public:
    explicit Circle(double radius) : radius_(radius) {}
    double radius() const { return radius_; }
    void accept(ShapeVisitor& visitor) const override {
        visitor.visit(*this);
    }

private:
    double radius_;
};

class Rectangle final : public Shape {
public:
    Rectangle(double width, double height)
        : width_(width), height_(height) {}
    double width() const { return width_; }
    double height() const { return height_; }
    void accept(ShapeVisitor& visitor) const override {
        visitor.visit(*this);
    }

private:
    double width_;
    double height_;
};
```

选择前先判断变化方向：若经常新增操作、很少新增元素类型，Visitor 合适；若元素类型不断增长，虚函数或 `std::variant` 加 `std::visit` 可能更清楚。访问者引用只在 `accept` 调用期间有效；若访问者把元素地址保存到以后使用，就必须重新审查元素生命周期。

### 4.11 解释器模式

**要解决的问题**：领域中有一套很小、稳定、可以组合的语法，需要把文本解析成抽象语法树再求值。它不是“用一堆字符串判断代替解析器”。

```cpp
#include <memory>
#include <stdexcept>
#include <utility>

class Expression {
public:
    virtual ~Expression() = default;
    virtual int evaluate() const = 0;
};

class Number final : public Expression {
public:
    explicit Number(int value) : value_(value) {}
    int evaluate() const override { return value_; }

private:
    int value_;
};

class Add final : public Expression {
public:
    Add(std::unique_ptr<Expression> left,
        std::unique_ptr<Expression> right)
        : left_(std::move(left)), right_(std::move(right)) {
        if (!left_ || !right_) {
            throw std::invalid_argument("Add requires two operands");
        }
    }

    int evaluate() const override {
        return left_->evaluate() + right_->evaluate();
    }

private:
    std::unique_ptr<Expression> left_;
    std::unique_ptr<Expression> right_;
};
```

`unique_ptr` 表示 AST 节点的独占树形所有权，构造函数维护“二元运算必须有两个子表达式”的不变量。真正语言还要处理词法分析、优先级、结合性、错误位置、整数溢出、递归深度和资源限制；语法稍复杂时应使用成熟解析库或生成器。解释器模式适合小 DSL，不适合重新发明通用编程语言。

#### 行为型模式怎样选

| 变化压力 | 优先候选 | 关键问题 |
|---|---|---|
| 运行时替换算法 | Strategy | 策略是否无状态、按值保存或由谁拥有？ |
| 一对多事件传播 | Observer | 订阅 token、回调寿命、重入和异常怎样处理？ |
| 请求要排队、撤销或记录 | Command | 参数快照与接收者寿命是否足够？ |
| 隐藏遍历表示 | Iterator | 结构修改后迭代器何时失效？ |
| 算法骨架固定、少数步骤变化 | Template Method | 继承耦合是否比组合策略更便宜？ |
| 多个处理者按序尝试 | Chain of Responsibility | 未处理、重复处理和链所有权怎样表达？ |
| 行为随有限状态转换 | State | 转换图和非法状态是否显式？ |
| 需要撤销/恢复 | Memento | 快照大小、验证和敏感数据如何处理？ |
| 组件协作形成网状依赖 | Mediator | 中介者是否正在膨胀成 God Object？ |
| 元素集合稳定、操作经常增加 | Visitor | 新增元素会修改所有 visitor；是否可用 `variant`？ |
| 小型稳定语法需要组合求值 | Interpreter | 解析、错误、深度和资源限制是否完整？ |

行为模式最容易隐藏控制流。调试时应能回答“下一步调用由谁决定、状态存在哪里、失败向哪里传播”，否则模式名称只会增加阅读成本。

### 5.2 工厂模式 vs 抽象工厂

| 对比项 | 工厂方法 | 抽象工厂 |
|--------|----------|----------|
| 目的 | 创建一种产品 | 创建产品家族 |
| 新增产品 | 新增工厂类 | 修改工厂接口 |
| 新增产品族 | 无需修改 | 新增工厂类 |
| 复杂度 | 较低 | 较高 |

### 5.3 装饰器 vs 代理

| 对比项 | 装饰器 | 代理 |
|--------|--------|------|
| 目的 | 增加功能 | 控制访问 |
| 对象创建 | 客户端 | 代理内部 |
| 关注点 | 功能扩展 | 访问控制 |

### 5.4 策略模式 vs 状态模式

| 对比项 | 策略模式 | 状态模式 |
|--------|----------|----------|
| 目的 | 算法切换 | 状态转换 |
| 客户端 | 选择策略 | 不知道状态 |
| 行为 | 独立算法 | 状态相关 |

### 5.5 设计模式面试题

```
常见面试题：

1. 如何实现线程安全的单例？
   答：简单场景使用 Meyers 单例；需要显式生命周期和测试替身时，由上层 owner 管理普通对象。基于普通指针的双重检查锁定有数据竞争，不能使用。

2. 工厂方法与抽象工厂的区别？
   答：工厂方法针对一种产品，抽象工厂针对产品家族

3. 装饰器模式的应用场景？
   答：Java I/O、C++ 流操作

4. 观察者模式的实际应用？
   答：事件系统、MVC 架构、消息队列

5. 如何选择创建型模式？
   答：
   - 简单对象：直接创建
   - 复杂对象：Builder
   - 需要复制：Prototype
   - 需要延迟：Proxy/Factory
```
