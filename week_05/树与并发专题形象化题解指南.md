## 🗺️ 先看两张不变量地图

### 树题：每次递归都在缩小哪棵子树

```text
调用前：node 是当前子树根的观察指针，树所有权仍在调用者
空节点：直接返回，不能继续解引用
递归步：只进入 left/right 指向的更小子树
调用后：树结构和所有权不变；结果满足本函数声明的追加/返回契约
```

所有树题都至少检查下面四个量：

| 量 | 要问的问题 | 常见错误 |
|---|---|---|
| `n` | 有多少个从根可达的节点？ | 只写 O(n) 却没有说明每个节点是否恰好访问一次 |
| `h` | 根到最深节点的层数是多少？ | 把平衡树的 O(log n) 递归深度当作所有树的保证 |
| `w` | 某一层最多有多少节点？ | 把 BFS 队列空间误写成 O(h) |
| 输出长度 | 是否要复制所有路径或序列化 token？ | 忽略答案本身可能远大于 O(n) 个整数 |

退化树中 `h` 可以等于 `n`，递归可能耗尽调用栈；显式栈把存储转到动态内存，但不会把 O(h) 空间变成 O(1)。课程树由 `unique_ptr` 形成独占所有权链，栈、队列和算法返回的裸指针都只是观察者，不能活过根对象。

### 并发题：先画状态，再谈 API

```text
共享状态 ──由同一把 mutex 保护──> 谓词
    │                               │
    ├─ 修改状态后通知 ──────────────┘
    │
    └─ unlock / lock、future 就绪或原子 release/acquire
       建立可证明的 happens-before
```

通知不是状态，睡眠也不是同步。条件变量等待者必须检查受互斥量保护的谓词；atomic 只覆盖它所执行的原子操作，不能自动维护多个字段的事务不变量。线程池和可关闭队列统一画成下面的生命周期：

```text
Running
  ├─ submit 先在线程池锁内入队：接受，任务必须最终完成
  └─ shutdown 先在线程池锁内关门：后续 submit 拒绝
                    │
                    v
                Draining ──队列清空、worker 退出──> WorkersExited ──外部 owner join──> Stopped
```

稳定测试通过 future、谓词、join 和最终容器状态证明完成；`sleep_for`、线程 ID、日志先后和“必须在若干毫秒内结束”都不是上述协议的一部分。

## 📚 Day 29: 二叉树遍历 - 树的基础

### 🎮 题目理解（生活类比）

```
二叉树:
        1
       / \
      2   3
     / \
    4   5

三种遍历方式:
- 前序: 根→左→右 → 1,2,4,5,3
- 中序: 左→根→右 → 4,2,5,1,3
- 后序: 左→右→根 → 4,5,2,3,1
```

```
想象家谱树:

前序（先拜访长辈）: 爷爷→爸爸→哥哥→我→叔叔
中序（左到右）: 哥哥→爸爸→我→爷爷→叔叔

```

```
递归调用栈:

visit(1):
```

```
前序遍历迭代版:
```

#### 遍历模板

下块是 LeetCode 形式的局部算法片段，**不可单独编译**；它省略了 `<vector>`、`<stack>`、`std::` 限定，并假定已有 `TreeNode { int val; TreeNode* left; TreeNode* right; }`。指针只借用在线评测管理的节点；放入独立项目时还要补上根节点所有者。

```cpp
// 前序递归
void preorder(TreeNode* root, vector<int>& res) {
    if (!root) return;
    res.push_back(root->val);  // 访问根
    preorder(root->left, res);  // 遍历左
    preorder(root->right, res); // 遍历右
}

// 前序迭代
vector<int> preorderTraversal(TreeNode* root) {
    vector<int> res;
    stack<TreeNode*> st;
    if (root) st.push(root);
    
    while (!st.empty()) {
        TreeNode* node = st.top(); st.pop();
        res.push_back(node->val);
        if (node->right) st.push(node->right);  // 右先入栈
        if (node->left) st.push(node->left);    // 左后入栈
    }
    return res;
}
```

#### BFS模板

下块是 LeetCode 形式的局部算法片段，**不可单独编译**；它省略了 `<vector>`、`<queue>`、`<cstddef>`、`std::` 限定，并复用上文的 `TreeNode` 原始指针接口。本课程实际工程中的树由 `unique_ptr` 拥有，队列中只保存观察指针。

```cpp
vector<vector<int>> levelOrder(TreeNode* root) {
    vector<vector<int>> result;
    queue<TreeNode*> q;
    
    if (root) q.push(root);
    
    while (!q.empty()) {
        size_t levelSize = q.size();  // 当前层节点数
        vector<int> level;
        
        for (size_t i = 0; i < levelSize; ++i) {
            TreeNode* node = q.front(); q.pop();
            level.push_back(node->val);
            
            if (node->left) q.push(node->left);
            if (node->right) q.push(node->right);
        }
        
        result.push_back(level);
    }
    
    return result;
}
```

## 📚 Day 31: 验证二叉搜索树 - BST性质

### 🎮 题目理解

```
BST（二叉搜索树）性质:
- 左子树所有节点 < 根节点
- 右子树所有节点 > 根节点
- 左右子树也是BST

        5
       / \
      3   7
     / \ / \
    1  4 6  8

验证: 每个节点都在合法范围内
```

### 🧠 范围验证法

#### 形象比喻：上下级关系

```
想象公司层级:
- 你的值必须在上级规定的范围内
- 上级给你的下级规定更窄的范围

        5 (范围: -∞, +∞)
       /              \
      3               7
(范围: -∞, 5)    (范围: 5, +∞)
     / \
    1   4
(-∞,3) (3,5)
```

#### 动画演示

```
树:     5
       / \
      3   7
     / \
    1   4

验证过程:

validate(5, min=-∞, max=+∞):
  5在(-∞, +∞)范围内 ✓
  ├─ validate(3, min=-∞, max=5):
  │    3在(-∞, 5)范围内 ✓
  │    ├─ validate(1, min=-∞, max=3):
  │    │    1在(-∞, 3)范围内 ✓
  │    │    子树为空 → 返回true
  │    └─ validate(4, min=3, max=5):
  │         4在(3, 5)范围内 ✓
  │         子树为空 → 返回true
  └─ validate(7, min=5, max=+∞):
       7在(5, +∞)范围内 ✓
       子树为空 → 返回true

所有验证通过 → 是BST
```

#### 代码模板

下块是 LeetCode 形式的局部算法片段，**不可单独编译**；它省略了 `<cstdint>`、`<limits>`、`TreeNode` 定义以及 `validate` 的前置声明。这里故意用 `int64_t` 开区间包住 `int` 节点的全部值域；若节点本身也是 `int64_t`，则应改用 `optional` 边界或中序单调验证，不能把类型极值当成严格哨兵。

```cpp
bool isValidBST(TreeNode* root) {
    return validate(root,
                    std::numeric_limits<std::int64_t>::lowest(),
                    std::numeric_limits<std::int64_t>::max());
}

bool validate(TreeNode* node, std::int64_t minVal, std::int64_t maxVal) {
    if (!node) return true;
    const std::int64_t value = node->val;
    
    // 检查当前节点是否在范围内
    if (value <= minVal || value >= maxVal) {
        return false;
    }
    
    // 递归检查左右子树
    return validate(node->left, minVal, value) &&
           validate(node->right, value, maxVal);
}
```

## 📚 Day 32: 二叉树最大深度 - DFS/BFS

### 🎮 题目理解

```
树的最大深度 = 从根到最远叶子的层数

        3
       / \
      9  20
        /  \
       15   7

深度: 3层 → 返回3
```

### 🧠 三种解法

#### 解法1: DFS递归

```
maxDepth(root) = 1 + max(maxDepth(left), maxDepth(right))

     3
    / \
   9  20
      / \
     15  7

计算过程:
maxDepth(3) = 1 + max(maxDepth(9), maxDepth(20))
            = 1 + max(1, 1 + max(maxDepth(15), maxDepth(7)))
            = 1 + max(1, 1 + max(1, 1))
            = 1 + max(1, 2)
            = 3
```

#### 解法2: BFS层序

```
统计层数:

队列: [3], 层数: 0

处理第1层:
队列: [9, 20], 层数: 1

处理第2层:
队列: [15, 7], 层数: 2

处理第3层:
队列: [], 层数: 3

返回3
```

#### 解法3: DFS迭代（栈）

```
栈元素: (节点, 深度)

初始: [(3, 1)]
最大深度: 0

弹出(3, 1):
最大深度 = max(0, 1) = 1
推入: (9, 2), (20, 2)
栈: [(9, 2), (20, 2)]

弹出(20, 2):
最大深度 = max(1, 2) = 2
推入: (15, 3), (7, 3)
栈: [(9, 2), (15, 3), (7, 3)]

...继续处理...

最终最大深度: 3
```

#### 回溯模板

下块是 LeetCode 形式的局部算法片段，**不可单独编译**；它省略了容器/字符串头、`std::` 限定、`TreeNode` 定义和 `dfs` 的前置声明。实际接口还应把工作区限定在一次调用内，以避免对象复用或并发调用时共享残留状态。

```cpp
vector<string> binaryTreePaths(TreeNode* root) {
    vector<string> result;
    vector<int> path;
    dfs(root, path, result);
    return result;
}

void dfs(TreeNode* node, vector<int>& path, vector<string>& result) {
    if (!node) return;
    
    path.push_back(node->val);  // 选择
    
    // 如果是叶子节点，记录路径
    if (!node->left && !node->right) {
        string s;
        for (size_t i = 0; i < path.size(); ++i) {
            s += to_string(path[i]);
            if (i < path.size() - 1) s += "->";
        }
        result.push_back(s);
    }
    
    dfs(node->left, path, result);
    dfs(node->right, path, result);
    
    path.pop_back();  // 撤销选择（回溯）
}
```

```
两个人往上追溯祖先:
- 你爸和你的公共祖先是爷爷
- 你和你兄弟的公共祖先是爸爸
- 你和自己的公共祖先是你自己

递归查每个人是否包含目标节点
```

#### 动画演示

```
树:     3
       / \
      5   1
     / \
    6   2

找LCA(5, 1):

LCA(3):
  左子树(5)找到了p ✓
  右子树(1)找到了q ✓
  左右都找到 → 当前节点3就是LCA

找LCA(5, 4):

  左子树找到了p(5)和q(4) ✓
  右子树什么都没找到
  → LCA在左子树

LCA(5):
  当前节点就是p → 返回5
  左子树找到了q(4)
  当前节点在pq路径上 → 当前节点5就是LCA
```

#### 代码模板

下块是 LeetCode 形式的局部算法片段，**不可单独编译**；它复用上文的 `TreeNode` 原始指针接口并省略所有权容器。返回值是对原树节点的非拥有观察指针，其有效期不能超过根所有者。

```cpp
TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
    // 基础情况
    if (!root || root == p || root == q) {
        return root;
    }
    
    // 在左右子树中查找
    TreeNode* left = lowestCommonAncestor(root->left, p, q);
    TreeNode* right = lowestCommonAncestor(root->right, p, q);
    
    // 左右都找到 → 当前节点是LCA
    if (left && right) return root;
    
    // 只有一边找到 → 返回找到的那边
    return left ? left : right;
}
```

这个短模板采用 LeetCode 的前提：`p`、`q` 都在树中。若把它放进通用库，必须定义缺失节点、空指针和 `p == q` 的行为；Week 5 工程版本会先检查两个观察者是否属于同一棵树，并用 `unique_ptr` 管理节点所有权。

## 📚 Day 34：LC 105 前序与中序重建二叉树

### 🎮 为什么两份序列能确定结构

前序的第一个元素一定是当前子树根；在中序中找到这个根后，左侧元素只属于左子树，右侧元素只属于右子树。于是“根是谁”和“左右子树各占多长区间”同时确定，再对两个区间递归即可。

```text
preorder = [3, 9, 20, 15, 7]
inorder  = [9, 3, 15, 20, 7]

前序首项 3 是根
中序按 3 切分: [9] | 3 | [15, 20, 7]
左子树消耗前序接下来的 1 项 [9]
右子树消耗剩余前序 [20, 15, 7]
```

递归函数最重要的不是“找到根”，而是区间契约。本仓库实现同时传入前序和中序的四个半开区间 `[pre_begin, pre_end)`/`[in_begin, in_end)`，并验证两个区间长度始终相等。另一种等价写法是只传中序区间并维护前序游标；两种写法都必须证明成功返回时恰好消费当前子树的节点数。父节点用 `unique_ptr` 独占左右子树，递归返回新子树根的所有权。

### 失败方式和工程契约

- 长度不同：两份序列不可能描述同一棵树。
- 元素集合不同：在中序区间中找不到前序根，必须拒绝。
- 重复值：仅靠“值到中序位置”的哈希表无法知道应选择哪次出现；本课程接口明确拒绝重复值。
- 游标提前耗尽或最后仍有剩余：说明区间划分或输入不一致。

朴素实现每层线性搜索中序位置，退化时为 O(n²)；预先建立值到位置的 `unordered_map` 后，在哈希操作平均 O(1) 的前提下构建平均 O(n)，但哈希严重退化时最坏仍可到 O(n²)。索引表占 O(n)，递归栈另占 O(h)，因而总额外空间为 O(n + h)=O(n)。实际契约测试见 Day 34 的 `day34_lc0105_contract_test`。

## 📚 并发主线（Day 29-34）：线程安全与同步

### 🎮 并发基础概念

```
并发问题: 多个线程同时访问共享数据

例子: 两人同时取钱
账户: 1000元
A取500，B取500
如果无同步读写普通余额变量，在 C++ 中首先是 data race 和未定义行为；“余额偶尔变500”只是可能观察到的一种现象
```

### 🧠 线程安全方案

#### 方案1: 互斥锁（Mutex）

```
互斥锁就像卫生间门锁:
- 一个人进去，锁门
- 其他人必须等待
- 出来后开锁，下一个人才能进

代码:
std::mutex mtx;
{
    std::lock_guard<std::mutex> lock(mtx);
    // 读取并更新同一组受保护状态
}  // 作用域结束自动解锁，异常路径也安全
```

#### 方案2: RAII锁管理

```
使用lock_guard自动管理锁:

{
    std::lock_guard<std::mutex> lock(mtx);
    // 访问共享数据
}  // 自动解锁，即使发生异常

类比: 自动门，人走后自动关
```

#### 方案3: 原子操作

```
原子操作: 不可中断的单步操作

std::atomic<int> counter(0);
counter.fetch_add(1, std::memory_order_relaxed);  // 独立计数只需要原子性

类比: 一个不可打断的动作
```

原子操作只保证它规定的单个操作；“先检查余额再扣款”或“同时修改两个字段”仍是复合不变量，通常需要 mutex。atomic 的实现也不保证一定无锁，`relaxed` 计数不会顺便发布其他普通数据。

### 线程安全计数器示例

```cpp
#include <mutex>
#include <atomic>

// 方案1: 使用互斥锁
class SafeCounter {
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mutex_);
        ++count_;
    }
    
    int get() {
        std::lock_guard<std::mutex> lock(mutex_);
        return count_;
    }
    
private:
    int count_ = 0;
    std::mutex mutex_;
};

// 方案2: 使用原子操作
class AtomicCounter {
public:
    void increment() {
        ++count_;  // 原子操作
    }
    
    int get() {
        return count_.load();
    }
    
private:
    std::atomic<int> count_{0};
};
```

## 📚 并发编程进阶 - 生产者消费者

### 🎮 问题理解

```
生产者: 生产数据放入缓冲区
消费者: 从缓冲区取出数据处理

问题:
- 缓冲区满了，生产者要等待
- 缓冲区空了，消费者要等待
- 需要线程安全的队列
```

### 🧠 条件变量

#### 形象比喻：餐厅等位

```
条件变量就像餐厅叫号:
- 没座位时，顾客等待（wait）
- 有座位时，服务员通知（notify）
- 被通知后，顾客醒来取号

std::condition_variable:
- wait(): 等待通知
- notify_one(): 通知一个等待者
- notify_all(): 通知所有等待者
```

#### 线程安全队列实现

```cpp
#include <condition_variable>
#include <mutex>
#include <optional>
#include <queue>
#include <utility>

template<typename T>
class ThreadSafeQueue {
public:
    bool push(T value) {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (closed_) return false;
            queue_.push(std::move(value));
        }
        cond_.notify_one();  // 通知消费者
        return true;
    }
    
    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        cond_.wait(lock, [this] { return closed_ || !queue_.empty(); });
        if (queue_.empty()) return std::nullopt;
        T value = std::move(queue_.front());
        queue_.pop();
        return value;
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            closed_ = true;
        }
        cond_.notify_all();
    }
    
private:
    std::queue<T> queue_;
    std::mutex mutex_;
    std::condition_variable cond_;
    bool closed_{false};
};
```

谓词才是状态，通知只是提醒等待者重新检查状态；因此 `wait(lock, predicate)` 同时处理“通知先发生”和虚假唤醒。`close()` 明确停止协议：拒绝新值、排空已接受值、空且关闭时返回 `nullopt`，这样消费者不会在生产者退出后永久睡眠。

### 任务、线程与 future 怎么选

- 需要一个返回值或异常时，优先把工作表达为任务并保存 future。
- 必须保证并发执行时，`std::async` 显式写 `std::launch::async`，否则默认策略可能 deferred。
- 需要长期 worker、线程属性或队列背压时，使用有明确 submit/close/join 契约的线程池。
- 普通 `future` 只有一个消费者，一次性事件可用 `promise<void>`；多个等待者使用 `shared_future`。
- joinable 的 thread 析构会终止程序，而 future 是否在最后释放时等待取决于共享状态来源，不能背成统一规则。

## 📚 Day 35：LC 297 序列化与反序列化

### 🎮 把形状也写进字符串

只记录节点值会丢失空孩子位置。前序格式把每个真实节点写成值、每个空指针写成 `#`，因此反序列化每读一个 token 就知道接下来要递归读取几个子树。

```text
    1
   / \
  2   3

前序带空标记: 1,2,#,#,3,#,#

读 1 -> 建根并继续读左右
读 2 -> 建左孩子并消费 #、#
读 3 -> 建右孩子并消费 #、#
最后 token 必须恰好耗尽
```

普通中序不能单独唯一编码任意二叉树。`#,1,#,2,#` 既可能是“1 的右孩子是 2”，也可能是“2 的左孩子是 1”；额外空标记仍未给平铺中序加入括号边界。可选方案是前序/后序加空标记，或层序按每个父节点的左右槽位记录。

工程格式还必须拒绝空字符串、开头/结尾/连续分隔符、部分整数 `12abc`、超出 `int` 的数、提前结束和完整树后的多余 token。`stoi` 若不检查消费位置会接受部分 token；仓库实现用 `from_chars` 并要求返回位置等于 token 末尾。反序列化返回 `unique_ptr`，异常发生时已经构造的部分树会自动释放。

时间复杂度 O(n)，其中 n 包括真实节点和空标记；前序递归的辅助栈为 O(h)，保存 token 的实现另占 O(n)。

## 📚 Day 35：LC 124 最大路径和

### 🧠 单臂返回值与双臂答案

递归返回给父节点的路径必须以当前节点为一端，所以只能选择左臂或右臂；但当前节点可以作为整条答案的最高转折点，此时左右两臂可以同时使用。

```text
        20
       /  \
     15    7

返回父节点的贡献: 20 + max(15, 7) = 35
以 20 为转折点的候选答案: 15 + 20 + 7 = 42
```

递归不变量如下：

1. 空孩子对父节点贡献 0。
2. 负贡献直接舍弃，因为路径可以不走那条子树。
3. 返回值只能是一条可继续连接父节点的单臂路径。
4. 全局最佳值比较当前节点的双臂候选；初始化必须是最小可表示值，不能用 0，否则全负树会错误选择空路径。

更宽整数类型只能扩大范围，不能消灭溢出。若公开接口允许节点取 `INT64_MAX`，再加一个正贡献仍会发生有符号溢出 UB；仓库版本用受检加法并抛出 `overflow_error`。时间复杂度 O(n)，递归栈 O(h)，退化树的 h 可到 n。

## 📚 Day 35：把知识变成项目证据

完成课程不等于记住全部 API，而是能为一个模块写出下面五类可审查信息：

1. **接口**：调用者能做什么，输入失败怎样报告。
2. **所有权**：谁拥有树节点、任务、线程和结果，观察者能活多久。
3. **不变量**：例如 BST 的全局上下界、路径回溯前后状态一致、线程池中每个已接受任务只完成一次。
4. **停止协议**：何时拒绝新工作，已接受工作排空还是取消，谁负责 join。
5. **验证证据**：正常值、空输入、极值、异常、重复关闭和并发路径都由会失败的测试覆盖。

运行每日 `build_and_run.sh` 后，不要只看“程序打印了什么”，要阅读 CTest 名称并故意制造一次失败，确认测试确实以非零状态阻止交付。Sanitizer 能发现已执行路径上的一部分内存和竞态错误，但它不是形式证明；测试也不应依赖线程输出顺序或固定睡眠时间。

## 💡 树与并发学习技巧

### 树的遍历总结

```
DFS（深度优先）:
- 递归: 代码简洁
- 迭代: 用栈模拟递归

BFS（广度优先）:
- 用队列实现
- 适合层序遍历；在无权图或每条边等权时可求最少边数

选择:
- 深度相关问题 → DFS
- 层级相关问题 → BFS
```

### 并发编程要点

```
1. 识别共享数据
2. 选择同步机制:
   - 简单计数 → atomic
   - 复杂操作 → mutex
   - 等待条件 → condition_variable
   
3. 避免死锁:
   - 按固定顺序加锁
   - 使用scoped_lock
   - 尽量缩短锁的持有时间
```
